# Code / Design 模式能力分离方案（DEC-2 收敛实现）

> 状态：**已落地**（2026-10-01，三提交：`3d938c82` / `68d31f81` / `2970b504`）。
> 决策依据：《改造计划》§6 `DEC-2`（design/code = agent preset，会话级切换；「共享插件树，须靠工具 scope 过滤防越界」）。本文记录诊断结论、用户拍板、落地架构与遗留项，是「两模式能力边界」的唯一参考。

## 1. 问题诊断（2026-10-01 分析结论）

两模式共享同一 agent 内核（deepagents）本身没问题（DEC-2 已拍板），但实现层四处混装：

1. **工具面全量共享**：`createMainAgentTools` 无条件注册画布三件套与生图生频，Code 会话全部带上。
2. **系统提示单份且纯 design 风味**：通篇画布操作表 / 颜色字号规范，Code 会话的 agent 拿着「设计师手册」干编码活，编码指导为零。
3. **`<canvas_state>` 无差别注入**：Code run 也带真实 canvasId（沙箱目录名载体），每轮都注入隐藏画布数据。
4. **两套 canvasId 口径分叉**：checkpoint 用 `sandboxScopeId ?? canvasId`（真实载体画布），画布工具用 `run.canvasId`（Code 无项目时是会话 UUID → `canvas_not_found`；有项目时真实写入**用户看不见的主画布**——静默成功型坏体验）。`screenshot_canvas` 在 Code 前端无 handler 必失败。

根因：Code 会话载体「方案 A」复用画布记录（隐藏「Code 工作台」项目 + 主画布，canvasId 兼作沙箱目录名），画布能力没有随 preset 收敛。

## 2. 用户拍板（2026-10-01）

| # | 决策 | 备注 |
| --- | --- | --- |
| 1 | **彻底分离**：Code 会话不携带任何画布能力（工具 / 提示 / canvas_state 三处全净） | future 的「Code 操作画布」设想以「显式目标画布」将来另行立项，本期不做半吊子保留 |
| 2 | **生图生频归 design**：Code 模式先剔除 | 产物当前只能落画布，Code 会话无处可去；「生图落沙箱」独立立项 |
| 3 | **直接对准注册表目标态**：不做参数化过渡层 | 无用户探索期，测试数据可弃，失败可回退 |
| 4 | **Design 侧 execute/文件工具本期不动** | 伤害小（提示不引导、无静默写画布），记遗留 |

产品口径重申（用户原话，历史日志）：「Code 模式是对话、Design 模式是画布」。

## 3. 落地架构

### 3.1 工具面：双通路，按依赖性质分界

| 通路 | 工具 | 原因 |
| --- | --- | --- |
| **内核注册表**（agent-runs 插件 `apply()` 向 `ctx.tools` 注册，`registry.list(preset)` 过滤） | `inspect_canvas` / `manipulate_canvas` / `screenshot_canvas` / `get_brand_kit`（scope=design） | 服务型依赖（canvasRepository / brandKit / connectionManager / blob）+ 静态 schema；per-run 上下文从 `execCtx` 取（`brandKitId` 由画布→项目 JOIN 在 execute 期重推导） |
| **装配点**（`createRunScopedTools`，deep-agent 按 preset 创建） | `project_search` / `persist_sandbox_file`（恒挂，shared）+ `generate_image` / `generate_video`（仅 design） | 运行态依赖：project_search 绑 per-run backend（grep 虚拟工作区）、persist_sandbox_file 路径守卫须与 backend 沙箱口径一致、生图生频 schema 内嵌工作区模型目录（注册表是启动期静态 schema）且提交闭包捕获 run 上下文 |

配套：
- `ToolDefinition` 增 `zodSchema` 逃生口，桥接层优先原生 zod——避免 zod → JSON Schema → zod 往返丢 default/union/enum（`parameters` 仍由 `z.toJSONSchema` 自动派生）。
- `ToolExecutionContext` 增 `userId`（画布截图 RPC 用户路由、品牌套件 `:user` 谓词）。
- `video_generate` 子代理随 `generate_video` 归 design（防 Code 下空工具带）。

### 3.2 系统提示：base + 模式段互斥

`prompts/compose.ts` 纯函数 `composeSystemPrompt`（唯一组装点）：

- **base**（两模式恒挂）：身份、工具选择总则（纯文字任务不调工具）、错误处理总则、语言规则；
- **design 段**：画布感知 / 生成工具路由 / manipulate 操作表 / 尺寸颜色字号 / 绘制顺序（原 kenfutwork-main 全文迁移）；
- **code 段**（新写）：工作目录作用域（多轮共享沙箱）、文件命令工具约定、`execute_background` 长命令、检查点（影子 git，勿手动 commit）、子代理（explore/review）、错误处理——**不提任何画布/生图能力**；
- 品牌套件段仅 design 且已绑定；Skills 段与插件提示段（含用户规则）两模式恒挂。

### 3.3 canvas_state 门控

`resolveCanvasStateForRun`：**仅 design 注入**。Code run 即使带真实 canvasId（项目主画布 / Code 工作台载体）也不再注入隐藏画布数据；仓储缺席 / 画布解析失败维持非关键降级（design 下可手动 `inspect_canvas`）。

### 3.4 fail-loud 加固

`resolveChildToolbelt` 缺名从静默跳过改为抛错：preset 过滤或装配漂移掏空子代理工具带时在派发期暴露，不派「没有手的专员」空转。

## 4. 远期：两模式打通（方向性共识，未立项）

用户判断：Codex 竞品已支持在编码会话直接生图（ChatGPT 与 Codex 合体、ChatGPT Work 基于 Codex），**打通本身不是问题**；但前提是**两个模式的能力先各自做强、好用**。当前不打通的核心障碍是数据流异构：

- Design 的资产在数据库（图片应存 S3 / 本地文件系统，当前链路未收口）；
- Code 操作用户机器的真实文件系统（编辑文件、跑 bash）。

打通前置条件（立项时逐项核对）：
1. Design 资产存储收口（S3 / 本地 FS 统一落盘协议）；
2. 「显式目标画布」工具设计（canvasId 参数 + Code UI 画布预览入口 + 跨项目授权语义）；
3. 生图产物落沙箱文件（Code 场景）与落画布（Design 场景）的双落点协议。

| 双 canvasId 口径（checkpoint vs 画布工具） | 画布工具已 design-only，分叉的实际伤害收敛为上一条 | 见上 |
