# 插件架构检查

> 角色：调研、源码快照与适配建议。日期：2026-10-22。
> 依据：KenFutWork `e0af10acd68ec22881f858f559f10bd98971442c` 及当时工作区；`profiles/server.ts` 含并行修改。
> 本文只检查源码与已有测试内容，未运行测试、启动服务或修改运行时代码。行为判断不等于应用验收。
> 服务定义以[《改造计划》](../方案设计/改造计划.md) §4.2 为准，扩展方式以该文 §4.10 为准；本文不维护副本清单。

## 判断

当前插件化已经可以支撑第一方功能按模块组合、服务替换、工具注册、审批和动态安装。
“插件化已经完美”的判断没有依据：事件注销、启动失败回收、安装状态恢复、通用在途调用管理仍有明确缺口。
第三方代码的运行隔离、公开插件能力范围、内部服务依赖约束也需要分别定义完成条件。

这里涉及三种不同对象，评估时应分别说明：

- 第一方 feature 插件：通过 `PluginDefinition` 与 profile 组合可信服务，可以使用完整宿主接口。
- 安装式 bundle：通过兼容门面贡献工具、提示、路由、界面入口和存储，支持运行中启停。
- MCP、Skills、媒体驱动：各自拥有协议、安装和生命周期；名字中都有“插件”不代表它们共享同一执行边界。

## 1. 事件订阅没有统一跟随插件注销

**分类：源码确认；优先级：高。**

[compat-context.ts](../../apps/server/src/features/plugins/compat-context.ts) L413–421 的 `ctx.on` 返回取消订阅函数，但没有把它加入该插件的资源释放列表。
L450–459 的清理只消费工具、显式 `effect` 和贡献物的释放函数。
因此，插件直接调用合法的 `ctx.on(...)`，没有再手动把返回值交给 `ctx.effect` 时，停用、卸载及 `apply` 失败都不会自动注销该监听器。
[context.ts](../../apps/server/src/kernel/context.ts) L810–811 的第一方入口也采用相同行为。

影响：已停用插件的 `pre-step`、工具审批或结束监听仍可能被调用；重新启用后可能重复订阅。
问题发生在后续事件派发：旧消费者仍然保留。

改动位置：由兼容门面和内核上下文统一登记事件订阅；取消订阅应幂等，兼容现有作者主动注销的写法。
同时核对第一方直接注册工具、提示与能力时是否完整保存了返回的释放函数。

验收条件：真实事件总线中连续执行安装、停用、启用、卸载、安装失败；每一步的调用次数符合当前安装态，卸载后的监听次数为零。
还要覆盖监听器主动注销、重复关闭及异步释放失败后再次关闭。

依赖：先明确“宿主管理订阅生命周期”的 SDK 规则，再补回归测试与实现。

## 2. 启动装配失败没有覆盖已创建资源的释放

**分类：源码控制流确认；实际资源遗留程度待故障注入验证；优先级：高。**

[compose.ts](../../apps/server/src/kernel/compose.ts) L171–197 在 `apply`、工厂实例化或 `mounted` 抛错时直接退出，L215 的释放句柄尚未返回。
[app.ts](../../apps/server/src/app.ts) L45–79 先调用装配，L88–92 才注册 `kernel.dispose` 的关闭钩子。
[server.ts](../../apps/server/src/server.ts) L111 的 `buildApp` 又位于 L138 的启动异常处理之前；末尾 L212–214 只报告错误并设置退出码。

正常 `app.close()` 会释放成功装配的内核，但上述构建失败没有经过这条路径。
若前序插件已经创建连接、循环或订阅，后序插件失败时，其清理动作没有统一执行机会。

改动位置：内核装配与应用入口共同承担启动事务的资源所有权；失败时等待已获得资源的释放，再报告启动失败。
复用已有异步释放机制，保留原错误与清理错误，不把“已开始关闭”当作“已关闭”。

验收条件：分别在 `apply`、服务工厂、`mounted` 注入异常；此前创建的真实监听端口、定时工作和连接关闭完成。
验证清理函数失败时错误可见，并保留可再次清理的句柄；成功启动和正常关闭行为不变。

依赖：与第一项共同使用统一的资源登记；若装配改为异步，入口与测试调用方必须同批更新。

## 3. 插件安装记录、运行状态和异常恢复尚未形成完整状态机

**分类：部分源码确认，异常中断恢复待验证；优先级：高。**

[plugin-registry-service.ts](../../apps/server/src/features/plugins/plugin-registry-service.ts) L381–383 把撤销屏障和版本备份路径保存在内存。
升级在 L779–801 依次移动旧目录、写新目录、加载新模块、保存库存；重启恢复 L1326–1353 只按库存重新加载。
其中缺少可持久读取的“正在替换、等待清理、等待恢复”阶段。进程在目录变更与库存提交之间结束后的行为，需要独立验证。

已确认的状态呈现问题：L1343–1346 启动加载失败只记录日志；L934–941 仍按旧兼容报告和 `record.enabled` 返回可用标记及清单入口。
同一服务 L385–390 还会吞并状态提交后的生命周期通知异常，调用方拿到的成功结果不包含激活失败事实。

影响：安装列表的“启用”不能可靠说明实现已加载；异常中断后，库存、运行副本和功能激活可能不同步。
L473–485 还会按安装时间复用临时运行副本，因此恢复测试必须同时覆盖运行副本存在与已被系统清理两种情况。

改动位置：安装记录保留用户期望状态，运行状态另行报告；为替换、卸载、恢复建立持久操作阶段与启动核对。
新实现与库存提交成功之前不得声明可用；清理未完成时保留可查询的原因和继续处理入口。

验收条件：在目录移动、新文件写入、模块加载、库存提交、数据清理处分别中断进程并重启；实际加载版本、目录、列表状态一致。
同一操作重试不重复执行插件业务动作；损坏入口、缺失目录和激活通知失败都能从接口读到。

依赖：先定义安装操作的幂等身份和持久阶段，再接启动恢复；同进程版本恢复测试继续保留。

## 4. 通用插件停用还缺少在途调用的宿主级管理

**分类：通用生命周期能力缺口；已有特定功能实现；优先级：高。**

内核在 [context.ts](../../apps/server/src/kernel/context.ts) L578–637 多次检查工具注册，能阻止旧审批或旧定义开始新的执行。
执行开始后，L637–649 等待工具自己的 Promise；[compat-context.ts](../../apps/server/src/features/plugins/compat-context.ts) L228–233 仅传递原 Run 的取消信号。
插件停用没有为该调用创建独立的插件撤销信号或通用在途登记。

HTTP 同样如此：[plugin-registry-service.ts](../../apps/server/src/features/plugins/plugin-registry-service.ts) L1139–1158 找到路由后直接等待其 handler。
L632–650 的卸载只等待插件自行登记的释放动作和可信宿主生命周期参与方，没有统一等待上述工具、路由调用。

影响：插件作者未自行管理在途工作时，停用返回后，先前开始的网络请求或存储写入仍可能完成。
已发出的外部副作用不能承诺撤回；需要区分“拒绝新调用”“请求取消”“确认工作结束”和“外部结果未知”。

改动位置：兼容执行适配器与路由派发器共同登记插件调用；停用先拒绝准入，再取消并等待受管理工作。
参照现有 [CAD 生命周期](../../apps/server/src/features/cad/operation-lifecycle.ts) L68–120 的确认方式，保留各领域对外部结果的判断。

验收条件：真实延迟请求和插件存储操作期间停用；没有新调用进入，停止回执与实际剩余工作一致。
覆盖忽略取消信号、无法确认停止、并发停用与重新启用；未知结果不得被新激活代际继承。

依赖：第一项资源所有权与第三项持久操作状态先形成一致规则。

## 5. 第三方 bundle 仍处于可信代码运行边界

**分类：明确设计限制；不能据此直接宣称已有利用事件。**

[plugin-registry-service.ts](../../apps/server/src/features/plugins/plugin-registry-service.ts) L519–525 在服务进程中 `import` 插件。
[compat-context.ts](../../apps/server/src/features/plugins/compat-context.ts) L22–24 明确兼容门面不提供安全隔离。
[module-scan.ts](../../apps/server/src/features/plugins/module-scan.ts) L59–121 使用文本模式识别能力和部分模块访问；安装检查通过只能证明符合这些兼容规则。

影响：Task 命令沙箱、工具审批和插件安装检查分别解决不同问题。
不能把“安装检查通过”解释为插件已受 Task 文件/网络边界保护，也不能把任意第三方模块当作低权限脚本运行。

改动位置：在开放更多插件来源前，明确可信第一方与外部包的信任规则；需要隔离的包通过受管理执行进程和受限宿主接口访问能力。
插件退出、异常、资源预算、文件/网络授权和凭据访问都应由宿主持有；文本扫描继续服务兼容性诊断。

验收条件：在隔离测试环境验证插件无法读取未授权文件、宿主秘密值或直接控制宿主进程；异常与长时间执行不会阻塞主服务。
验证工具声明的 `read` 与实际可访问能力一致；只声明权限等级不能替代执行约束。

依赖：沿用执行基础设施和第四项生命周期；隔离范围先写入权威规格，再实施 SDK 与运行提供方。

## 6. bundle 的模式声明没有统一作用于工具和提示

**分类：源码确认的消费不一致；完整界面影响待验证。**

[plugin-contracts.ts](../../packages/shared/src/plugin-contracts.ts) L120–121 接受 `design/code/shared` 作用域。
[plugin-registry-service.ts](../../apps/server/src/features/plugins/plugin-registry-service.ts) L851–860 按该声明筛选技能包。
但 [compat-context.ts](../../apps/server/src/features/plugins/compat-context.ts) L280–287 把所有 bundle 工具固定注册为 `shared`；加载参数 L525–595 未传入包作用域。
[prompt-sections.ts](../../apps/server/src/features/agent-runs/prompt-sections.ts) L110–123 对两种模式追加全部插件提示。

影响：声明仅供 Code 使用的包，其技能发现与工具、提示出现范围可以不同；模式专属能力可能进入另一模式的工具目录。
这里确认的是发现范围，执行仍经过现有角色、权限和 Task 检查。

改动位置：在 bundle 进入宿主时固定有效作用域，工具、提示与技能共同消费；旧包未声明时的默认行为保持明确。
不要只在界面过滤，工具注册、发现和执行检查必须使用同一来源。

验收条件：分别安装 Code、Design、shared 包，在两种模式中核对工具目录、技能和提示；运行中重装后旧 Run 不获得新模式能力。

依赖：复用已有工具贡献快照，补提示贡献的模式信息；无需增加 Agent 循环。

## 7. 后台执行器仍使用独立的进程全局注册表

**分类：实现边界限制；当前生成任务可运行，不代表扩展机制完整。**

[job-executor.ts](../../apps/server/src/features/jobs/job-executor.ts) L52–64 使用模块级 Map；注册会直接覆盖同名执行器，没有所有者、注销函数或配置版本。
[job-loop-plugin.ts](../../apps/server/src/features/jobs/job-loop-plugin.ts) L4–6 通过副作用 import 安装执行器；
[job-loop.ts](../../apps/server/src/features/jobs/job-loop.ts) L24–36 仍单独维护队列、任务类型和可见性时间的映射。

影响：新增任务类型仍要同步修改多处；同进程多个内核、测试替换或将来允许插件贡献执行器时，注册状态不能随内核独立关闭。
现有图像与视频执行器在桌面和 worker 共用，这是已经完成的部分。

改动位置：让队列定义与执行器由同一个可信贡献入口登记；重复注册立即报错，退出时按所有权注销。
持久任务必须固定所需执行器版本及恢复规则，不能在恢复时默认使用同名的新实现。

验收条件：新增一个真实任务类型仅贡献定义和实现；两个内核分别注册、关闭时互不影响。
覆盖同名冲突、等待中卸载、运行中撤销、重启后的版本缺失与重复消息。

依赖：先在权威扩展机制中明确后台任务与插件生命周期关系；保留现有队列幂等、取消和结果发布行为。

## 适配顺序与验收范围

1. 先补事件所有权与启动失败释放，使每个插件具备可确认的生命周期。
2. 再补安装操作持久阶段、实际加载状态和在途工作管理，确保启停与重启结果一致。
3. 接着统一包作用域、依赖声明检查和后台执行器贡献方式。
4. 对需要开放给外部作者的能力建立受限执行边界，再扩展公开 SDK。

当前第一方服务通常具备接口、实现和消费者；公开 bundle 只提供受支持的能力集合。
[capability-binding.ts](../../apps/server/src/features/plugins/capability-binding.ts) L33–115 对模型、会话、文件、进程、子代理和后台任务保持显式不支持。
这符合当前兼容范围，后续增加能力应提供完整的授权、执行、退出与恢复行为，不能只开放一个服务对象。
