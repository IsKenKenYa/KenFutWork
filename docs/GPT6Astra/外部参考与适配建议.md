## 参考对象与适配位置

### 1. Codex：把会话控制做成明确协议

**已核实事实：**[App Server 官方文档](https://learn.chatgpt.com/docs/app-server)公开 thread、turn、item 的生命周期，提供恢复、分叉、运行中指导及审批请求；实验接口需要客户端声明能力。
原 `developers.openai.com/codex/app-server/` 本轮跳转至上述地址，本文使用实际读取到正文的地址。
**值得采用：**分别定义开始、继续、取消、审批、恢复与事件读取，客户端根据能力决定入口；保留明确的命令响应与运行结果边界。
**KFW 位置：**已有 [AgentRuntimeProvider](../../apps/server/src/agent/provider-contract.ts)（34–60 行）与 [Code UI service](../../apps/server/src/features/code-ui/service.ts)，可以承接外部协议适配。
**适配前提：**列明外部 thread/turn 与本地 Task/Run 的对应关系，确认取消完成、审批归属、断线后事件读取以及运行时原生历史的所有者。
**不能推断：**接口名称相似不证明数据与恢复行为兼容；外部引擎执行了工具，也不证明该操作经过 KFW 授权。

### 2. DeepSeek Harness：持久化保证写进接口定义

**已核实事实：**`references/deepseek-harness/README.md` 描述插件组合架构；`references/deepseek-harness/packages/session/session-persistence/src/handle.ts`（45–109 行）分别定义 append 的可见性与 flush 的持久保证。
`references/deepseek-harness/packages/session/session-persistence/src/storage-contract.ts`（69–103、145–150 行）拒绝未知必需事件与不连续序号；`references/deepseek-harness/packages/session/session-persistence/README.md` 说明单写者和中断后未知工具结果的处理。
**值得采用：**让所有持久化实现遵守相同的行为测试，明确哪个响应已经保证重启后可恢复。
**KFW 位置：**[工具执行凭据](../../apps/server/src/agent/tool-execution-receipts.ts)、[Task Work](../../apps/server/src/features/task-work/service.ts)与现有数据库持久化。
**适配前提：**先说明数据库提交、运行事件发布、外部操作凭据各自的成功边界，再验证响应丢失、重复命令和进程退出。
**不能推断：**DSH 的单写者接口本身不提供所有后端的跨进程排他保证；其 JSONL 方案也不构成替换 KFW Postgres 的依据。

### 3. ZCode：复用声明兼容与结构化 Hook 机制

**已核实事实：**参考目录中的 `apps/zcode-cli/packages/adapters/src/plugins/index.ts`（105–112、193–212 行）识别 ZCode、Claude、Codex 三种插件清单，并汇入 MCP、Hooks、Skills、Commands。
`apps/zcode-cli/packages/core/src/hooks/types.ts`（54–85 行）定义匹配条件、执行来源、超时及结构化控制结果；`tool/executor/hook-flow.ts`承载工具前后与权限请求 Hook。
**值得采用：**把外部声明转换为已有能力定义，给出逐组件兼容报告；使用统一的 Hook 输入、结果和生命周期。
**KFW 位置：**[Bundle 解析](../../apps/server/src/features/plugins/bundle-manifest.ts)、[用户 Hooks](../../apps/server/src/features/settings/hooks.ts)及[受 Task 约束的 Hook 执行](../../apps/server/src/features/settings/scoped-hook-command.ts)。
**适配前提：**保留安装检查、Task 目录、权限上限、取消与输出预算；声明式资源与可执行代码分别授权。
**不能推断：**ZCode 当前把 `lspServers` 等字段列为只报告诊断的组件；同文件 371–375 行对插件 Hook 直接放行的策略不能直接迁入 KFW。

### 4. Kimi Code：公开能力矩阵，区分恢复与重新播放历史

**已核实事实：**[官方 ACP 文档](https://moonshotai.github.io/kimi-code/en/reference/kimi-acp)分别说明 `session/load`、`session/resume`、fork、cancel、附加目录与不支持的方法。
当前 `references/kimi-code/packages/acp-server/src/session.ts`（1–20 行）通过 Klient 接口与事件映射驱动会话，并注明部分服务未接入该接口的限制。
**值得采用：**将能力声明、真实执行与客户端展示一起核验；“恢复会话”和“向客户端重新播放历史”分别定义。
**KFW 位置：**[Provider 接口](../../apps/server/src/agent/provider-contract.ts)、[会话连接](../../apps/server/src/features/code-ui/connections.ts)及[上下文历史](../../apps/server/src/agent/native-context-history.ts)。
**适配前提：**明确是否恢复原生状态、是否只读取历史、是否重新执行，以及运行中取消和晚到事件的处理。
**不能推断：**ACP 支持列表不代表所有原生命令均可用；官网能力与本地提交必须分别记录，不能用其中一个覆盖另一个。

### 5. OpenCode：按需提供代码语义服务与编辑器接入

**已核实事实：**[LSP 官方文档](https://docs.opencode.ai/docs/lsp/)本轮正文明确写明默认关闭，并说明内存、同步、版本和延迟代价；启用后可使用语言服务诊断。
[ACP 官方文档](https://docs.opencode.ai/docs/acp/)提供 stdio JSON-RPC 接入，同时明确部分内置命令如 `/undo`、`/redo` 不支持 ACP。
**值得采用：**把 LSP 作为按项目启用的代码语义服务；为编辑器提供能力明确的接口，不要求所有客户端拥有同样操作。
**KFW 位置：**现有[文件工具](../../apps/server/src/features/code-tools/tool-definitions.ts)、[进程沙箱](../../apps/server/src/features/process-sandbox/types.ts)和 [Provider 接口](../../apps/server/src/agent/provider-contract.ts)。
**适配前提：**语言服务必须受 Task 授权目录约束，处理文件版本、过期诊断、进程退出、资源预算和多项目隔离。
**不能推断：**LSP 存在不保证完成率提高；是否启用应通过本项目任务测量，lint/typecheck 仍承担实际检查。

### 6. Claude Code：完成检查、协议生态与可重复评测

**已核实事实：**[Hooks 文档](https://code.claude.com/docs/en/hooks)定义工具前后、权限请求、Stop 等事件的控制能力；[MCP 文档](https://code.claude.com/docs/en/mcp)包含 resources、prompts、elicitation 与动态清单更新。
[插件评测正文](https://code.claude.com/docs/en/plugin-evals)已重新读取，公开真实模型重复运行、结果评分及有无插件的对照；[SDK 观测文档](https://code.claude.com/docs/en/agent-sdk/observability)提供模型、工具和子代理关联，traces 标为 beta。
**值得采用：**用明确的检查结果决定能否结束；将工具发现、用户交互、执行结果与可观察事件连通，并保留改动前后的重复评测。
**KFW 位置：**[Hooks](../../apps/server/src/features/settings/hooks.ts)目前只有 turn-start/end；[MCP 接口](../../apps/server/src/features/mcp/mcp-tools.ts)目前主要是 listTools/callTool；[ToolSearch](../../apps/server/src/features/tool-catalog/catalogue.ts)和[Goal 评估](../../apps/server/src/features/goals/evaluation.ts)已有基础。
**适配前提：**优先扩展已有能力；Hook 不得越过权限上限；MCP 更新不能无声扩大当前 Run 的能力；评测使用真实实现与独立验收。
**不能推断：**官网文档可读不证明本机账号能运行每项功能；本文未执行 Claude 评测，也不把其评分方式直接当作 KFW 产品验收。

### 7. OpenHands：将 Agent、会话与执行环境分开

**已核实事实：**[SDK 架构正文](https://docs.openhands.dev/sdk/arch/overview)分别定义 Agent、Conversation、Workspace、Tools 与 Agent Server；本地与容器/远端执行共用 SDK 接口。
该文同时说明工具与 Agent 运行在所选环境中，不能把 Workspace 接口误解成所有工具操作必经的独立权限代理。
**值得采用：**让执行环境的创建、连接、关闭与 Agent 决策独立演进，清楚记录资源所有权。
**KFW 位置：**[执行作用域](../../apps/server/src/features/execution/scope-service.ts)、[ProcessSandbox](../../apps/server/src/features/process-sandbox/types.ts)和 [Task Work](../../apps/server/src/features/task-work/service.ts)。
**适配前提：**先明确会话运行在哪里、工具运行在哪里、谁持有凭据、谁负责停止与删除；外部目录和用户环境不得跟随临时资源清理。
**不能推断：**该架构说明不证明 KFW 需要增加云服务、容器或新账户系统；运行环境与现行本地实例边界仍须遵守本项目规格。

### 8. Aider：有预算的代码地图与编辑后反馈

**已核实事实：**[Repository map](https://aider.chat/docs/repomap.html)按相关性与 token 预算选择符号、类型和调用签名；[lint/test 文档](https://aider.chat/docs/usage/lint-test.html)支持编辑后运行检查并将失败结果反馈给模型。
**值得采用：**代码检索先提供可导航的摘要，需要时读取原文件；让编辑结果尽快接受真实检查。
**KFW 位置：**[项目搜索](../../apps/server/src/features/code-tools/project-search.ts)、[目录指令](../../apps/server/src/features/code-tools/project-instructions.ts)、[上下文预算](../../apps/server/src/agent/native-context-budget.ts)及现有命令执行路径。
**适配前提：**复用已有检索能力，给索引标注文件版本与来源；检查命令、工作目录和并发应经过 Task 调度。
**不能推断：**摘要不能替代当前源码；自动执行的 lint 或测试只证明其实际覆盖范围，不能证明全部业务行为正确。

## 来自公开工程实践的五项建议

以下为研究者对 KFW 的建议，参考依据与建议本身分别列出；不新增现行架构决策。

### 1. 用真实任务衡量 Harness 改动

**公开依据：**[Anthropic 工具工程](https://www.anthropic.com/research/writing-tools-for-agents)建议使用真实工作流、可核查结果与保留测试集，同时记录工具错误、耗时和 token；Claude 插件评测提供重复运行与对照思路。
**建议：**固定模型配置、项目起点、工具版本和验收命令，覆盖文件修改、长任务、压缩后继续、取消、重启、权限撤销及外部副作用未知等任务。
**验收：**比较改动前后的完成率、真实检查结果、耗时与消耗；保留全部失败，不能只选择成功样例。Goal 的单次判断与一组版本回归评测分别记录。

### 2. 让 Agent 读取当前环境的检查结果

**公开依据：**[OpenAI Harness engineering](https://openai.com/index/harness-engineering/)描述为每个工作目录提供隔离应用实例及可查询日志、指标与 traces，并将架构规则放入机械检查。
**建议：**将运行记录、进程状态、权限等待和实际文件版本关联到 Task/Run；检查失败返回可执行的处理信息。
**验收：**Agent 能从同一任务中定位失败阶段，并证明修复后原场景通过；新增环境检查不得扩大 Task 权限，也不自动授予发布或清理权限。

### 3. 上下文摘要必须能够追溯原始记录

**公开依据：**[Anthropic 上下文工程](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)讨论按需读取、压缩、结构化记录与子代理隔离；Aider 展示有预算的代码地图。
**建议：**继续使用 KFW 已有 [ReadHistory](../../apps/server/src/features/context-history/read-history-tool.ts)，为摘要保留来源、时间、所属 Run 与文件版本；持续保留用户限制和未完成事项。
**验收：**压缩后能够找回关键证据，正确区分旧状态与当前状态，并能在权限变化后拒绝历史指令所要求的越权操作。

### 4. 用工具选择和执行结果验证工具设计

**公开依据：**Anthropic 工具工程强调明确用途、命名、相关结果与评测，指出重叠工具和过量输出可能增加错误。
**建议：**在现有 ToolSearch 与工具注册表上测量误选、参数错误、重复查询及输出截断；按真实失败调整描述、schema 和分页，保留必要的底层工具。
**验收：**改进后在相同任务中减少无效调用，且没有减少授权检查或必要输出；工具数量和提示词长度本身不作为成绩。

### 5. 外部引擎升级按行为矩阵验收

**公开依据：**Codex 的实验能力声明、Kimi 的 ACP 能力表和 DSH 的持久化边界都明确区分“支持什么”与“何时保证完成”。
**建议：**每个引擎维护版本、输入类型、工具执行归属、审批、指导、取消、恢复、历史读取和分叉能力表；不支持的能力在接口与界面共同表达。
**验收：**升级后分别验证正常运行、断线、响应丢失、部分工具结果、取消后晚到事件与权限撤销；保持 KFW 的 Task、Run 和真实执行凭据为宿主事实。

## 采用顺序与结论边界

建议先完善真实任务验收、持久化边界与观测，再扩展 Hook、MCP 协议面及插件声明兼容；外部引擎和 LSP 按具体使用需求进入同一套验收。
KFW 已有 ToolSearch、历史读取、文件恢复与 Goal 独立评估，后续工作应补齐缺少的连接与证明，不重复创建同名能力。
本轮证据支持上述机制比较及适配建议；没有完成跨产品同任务实测，也没有证明任一外部引擎可以直接替换当前生产运行时。
