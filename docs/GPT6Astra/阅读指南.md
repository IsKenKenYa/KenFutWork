## 建议次序

1. 先验证现有路径：技能模式和加载错误、插件资源释放、共享目录自动提交、模型请求治理。先增加能复现行为的测试，再修改代码。
2. 同时建立固定任务验收和诊断记录。真实数据库、模型协议、真实模型、界面、发布产物分别记录结果。
3. 完善日常工作：受限联网、命令分段返回与 PTY、批量搜索、目录规则、子代理消息。
4. 在前面能力稳定后扩展：长期记忆、语言服务、外部插件声明、第二运行时、持久自动化。

这些是建议的依赖顺序。独立缺陷可以先修；新增产品行为回到其所属规格明确范围。

## 给执行 Agent 的要求

- 先读本次条目和其中引用的所属规格，再查当前源码。旧行号、历史测试数量和上游版本只用于定位。
- 区分四类结果：源码确认、待复测问题、已有实现但待验收、建议或未来规划。找到接口或文件不等于真实入口可用。
- 每批明确文件范围、依赖和完成条件；保留共享 Task/Run、Code/Design、LocalActor、授权版本和现有工具执行服务。
- 使用现有模块扩展。新的声明必须有真实消费方；工具成功必须来自实际执行结果；状态不明的外部写入不能自动重放。
- 先检查并行修改与正在运行的测试；按仓库规则串行验证、分批提交。不要根据本目录中的建议更改其他工作者的代码。
- 完成后更新所属规格的实施状态和[日志](../日志.md)，在本目录条目留下结果引用。本目录不重复保存每次运行的日志或测试总数。
