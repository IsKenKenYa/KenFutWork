## 2. 状态如何判定

| 状态 | 判定条件 | 后续动作 |
| --- | --- | --- |
| 已有实现 | 找到真实提供方、消费方以及对应提交或实现记录 | 复用现有能力，按改变的行为验证 |
| 待接入 | 产品需要的完整调用路径仍缺少；明确返回不可用也属于此类 | 连接实际服务，并保留失败和权限语义 |
| 待验收 | 已有实现，仍缺目标环境或完整用户流程的证据 | 先确定验收对象和结果，再安排执行 |
| 未来待决策 | 本期只写规格，或关键选择仍未批准 | 保留问题与来源，不作为当前缺陷修复 |
| 进行中 | 工作区或近期批次正在实现，尚未形成完整交付 | 与所属任务协调，核对提交和验证结果 |

同一功能可以同时包含已实现部分和待接入部分，例如媒体文件版本管理已实现，执行器和设置页仍需连接。
“默认跳过”“仅源码检查”“隔离服务验证”“真实桌面操作”“真实外部模型”分别记录，不能互相替代。

### 证据冲突时如何更新

| 出现的情况 | 处理方式 |
| --- | --- |
| 代码已有消费者，旧规划写未开工 | 记录当前提交和实际路径，修改当前状态，保留历史验证范围 |
| 日志说已完成，当前消费者找不到 | 先核对后续删除、替换及构建入口，暂不宣布实现缺失或可用 |
| 当前只有未提交文件 | 标记进行中，向所属任务核对，不代为提交或宣称完成 |
| 测试文件存在但默认跳过 | 只能说明有验证入口，取得实际执行结果后再更新验收状态 |
| 上游有能力，当前适配只有界面 | 按实际宿主能力标待接入，继续核对提供方和消费方 |
| 早期决定与后续确认不同 | 当前说明引用后续已确认规格，历史理由保留日期与适用范围 |

来源和结果分开保存：代码说明调用路径，日志说明某次执行，规格说明应满足的行为。
只有三者对应同一功能与边界时，才能将该项更新为已完成。

## 8. 建议的整理和执行次序

1. **校正入口状态。** 更新地图、原规格的当前状态与已提交批次，完成条件是入口不再指向已退役行为或误写未开工。
2. **接续已开展批次。** ZCode 与媒体供应商按原依赖继续，提交与验证归所属任务；完成条件是每批真实消费者、来源和证据齐全。
3. **处理共享能力的实际问题。** 按 Harness 改进清单先复测，再实施；完成条件是原症状及边界回归通过，不增加重复服务。
4. **补齐有限验收。** 根据第 5 节逐项安排目标环境；完成条件是实际输入、工具、产物、状态和独立读回能够对应。
5. **安排新增基础设施。** 记忆、调度、定义管理等按用户优先级单独制定实施范围；先明确所有权、权限、停止和恢复。
6. **讨论未来阶段。** Work、移动和远端服务在现有边界内逐项确认，引用原权威文档，不从参考项目整套引入。

建议将“尚无实现”和“已有实现但证据不足”分开认领，防止验收任务扩大成无关重写。
同一功能的完成依据只维护在原规格与日志中；本索引用一句状态和链接帮助导航。

## 9. 后续 Agent 的交接要求

开始某一项工作时：

1. 读取当前仓库指南、文档地图及对应规格的最新状态段。
2. 检查当前 HEAD、工作区改动和该功能最近提交，确认哪些代码属于并行任务。
3. 找到实际入口、服务、存储与消费方；旧文件名或 UI 页面存在不作为功能结论。
4. 将当前请求写成有限完成条件，列清已有能力、需要修改的行为与必要验证。
5. 若证据与本表不同，更新原属主文档和日志，再调整本索引；不要恢复旧施工指令。

交付或交接时至少留下：

- 已提交 SHA，以及该批解决的具体行为。
- 尚未提交的文件／修改段、用途、归属与未完成原因。
- 实际执行的完整命令、通过／失败／默认跳过和外部条件。
- 当前用户场景的验证结果；未执行的模型、GUI、平台和部署检查明确列出。
- 下一步依赖的确定事实，以及仍需用户决定的问题。
