## 1. 产品定位 ✅

### 1.1 目标用户与使命

- **v1 首要用户**：独立创作者 Prosumer（设计师、自媒体、AI 重度用户）。
- **产品使命双重性**：
  1. Prosumer 的 **Work Agent 工作台**——不只 AIGC 创作；
  2. 团队**锻炼自家 Agent Harness 能力**的载体——harness 是一等子系统，不是支撑设施。
- 团队/自部署 SaaS 是后置扩展方向，由插件架构（一切皆插件、皆可部署）承接，不影响 v1 范围。

### 1.2 产品本质与北极星

- **产品演进主线：从 Coding Agent 到 Work Agent**——本地终端执行（沙箱优先）、本地文件访问、各类能力操控。
- **画布只是形态之一**：AIGC 创作是 Work 的一种但不是全部；画布可以承接文字，但不强求承接一切。
- 对标：Trae Work、WorkBuddy、CodeBuddy、OpenClaw、CodeX、nomifun（本机能力 × 画布 × 精选 harness）。
- **北极星场景（验收标准）**：沙箱终端任务闭环——用户描述任务 → agent 在沙箱（默认 `workspace-write`）里跑终端/读写文件 → 危险操作弹窗提权 → 结果在工作台展示（文件树 / 终端 / 画布）。该旅程必须丝滑到无跳出。
- **战略洞察：终端 = 通用集成缝**。各家 AI 能力都有 CLI（Claude Code、Codex、Gemini CLI 等），沙箱终端让 harness 直接执行外部 AI CLI——**绕过各家 SDK、官方合作、APPID 授权**。
  - v1 深度：**命令级黑盒集成**——用户在终端 UI 直接用任意 CLI；agent 也能在沙箱里执行 `claude -p` / `codex exec` 并把输出当工具结果，不解析结构化流。
  - v2 方向：CLI Provider 适配层（流式输出、进度、diff、会话续接），独立 provider 缝承接。

| 能力 | v1 状态 | 备注 |
| --- | --- | --- |
| 沙箱终端任务闭环 | **新增，北极星** | 默认 workspace-write；危险操作弹窗提权 |
| 画布 | 保留，形态之一 | nomifun 本机能力 × 画布的结合 |
| 图像生成 | 保留 | BYOK 供应商缝的主要验证场 |
| 视频生成 | 保留，降级 | 优先级低于图像 |

## 2. 领域模型 ✅

### 2.1 开发姿态

- **破坏性开发自由**：0 用户、独立仓库、无历史数据兼容负担；像 nomifun 一样快速迭代、允许破坏性变更（与 deepseek-harness「pre-release: foundation over blast radius」立场一致）。首发 tagged release 前不写兼容层。

### 2.2 核心实体结构（统一 Task 模型）

```text
Workspace（用户域，v1 单用户本地，概念保留供多端）
  └─ Project（工作容器：文件夹/沙箱根 + 任务集合 + 产出物）
       ├─ Task（一等交互容器，吸收 Thread：对话即 Task 的交互面）
       │    └─ Run ×N（agent 单次执行：工具调用 + 事件流）
       └─ Canvas（Project 级可视化编排视图；Task 产物引用，不绑定）
```

- **Task 吸收 Thread**：不设独立聊天实体；chat 入口是 `kind=chat` 的 Task，终端任务是 `kind=work`。
- **Project 绑定文件夹**（桌面端 Work 思维）：新建/打开项目时选择本地文件夹，该文件夹即沙箱 `workspace-write` 的可写根，项目内所有 Task 共享；服务端部署时由系统分配托管沙箱目录。
- **默认项目**收口无项目对话（Work 产品惯例：空项目对话 / 无项目对话）。
- Canvas 降为 Project 级视图：Task 的产物（图/视频/文件）可被画布引用，但不强制绑定。

### 2.3 权限模型（双层）

- **OS 沙箱封外圈**（拦「能不能」）：`read-only` / `workspace-write`（默认可写根 = 项目文件夹）/ `danger-full-access`。
- **审批缝管逐操作**（拦「改前问不问」）：文件编辑 / 危险命令的同意门 + 一次性行内提权。
- **产品四档 = 两层预设组合**（Task 内可切换，对标各家 Coding Agent 通用惯例）：

| 产品模式 | 沙箱档 | 审批门 |
| --- | --- | --- |
| 计划模式 Plan | read-only | 编辑前先出计划 |
| 变更前确认 Ask | workspace-write | 每次改文件先问 |
| 自动编辑 Auto Edit | workspace-write | 文件编辑自动；危险命令仍审批 |
| 完全访问 Full Access | danger-full-access | 最少确认 |

- 沙箱执行后端选型（macOS Seatbelt / Linux Landlock / Windows ACL，或开源方案）**待调研**（见 §6）。

### 2.4 词汇表

见仓库根 `CONTEXT.md`（与代码/文档同步演进）。核心区分：**Task**（用户工作项，吸收对话）≠ **Job**（后台队列执行单元，现有图/视频生成任务）≠ **Run**（agent 单次执行）。

## 3. 内核缝接口 ✅

> 决策过程：Design It Twice——4 个并行子代理分别以「极简接口 / 全生命周期 / Fastify 原生 / Cordis 移植」视角设计后综合。调研佐证：Codex CLI 与 nomifun 均为小而显式的组合根（无反射式 DI 内核），DSH 的 Cordis 迭代过快仅作方向参考。

### 3.1 方案：avvio 引擎 + 返回值认领 + deps 注入

- **不自研 compose 引擎**：`inject` 编译为 fastify-plugin 的 `dependencies` 元数据，拓扑排序、环检测、缺失依赖 fail loud、`onClose` 逆序回卷全部复用 avvio（Fastify 5 / fastify-plugin 6 已验证的成熟机制）。
- **无服务定位符**：依赖不通过 `get(key)` 查找——`definePlugin` 用 const 泛型把 `inject` 字面量推断为精确类型的 `deps` 参数，由内核组装后传入；服务靠 `apply` **返回值认领**（内核 decorate 到根实例）。
- **dump 可观测**：`dump()` 返回挂载树快照（插件名 / enabled 结果 / provides / inject），dev 打表 + 作为 enabled 判定的测试断言面。
- **overrides 替身**：deps 组装时命中 overrides 的 key 跳过 factory——取代 `BuildAppOptions` 的 17 个测试覆盖项。
- **profile 分树**：`server` / `worker` / `desktop` / `test` 各自的插件清单引用同一批插件定义；worker = 同一 compose 函数 + 不 listen 的 Fastify 容器（复用同一套 onClose 生命周期）。

### 3.2 接口签名

```ts
// apps/server/src/kernel/types.ts
import type { FastifyInstance } from "fastify";
import type { ServerEnv } from "../config/env.js";

/** ctx key 稳定契约（插件化计划 §4.2 的类型投影；新增/更名同步该表，编译器强制） */
export interface ServiceMap {
  viewer: ViewerService;
  /* projects / brandKit / canvas / threads / chat / settings / uploads / jobs / credits
     / tierGuard / payments / generation / modelProviders / modelCatalog / auth / backend / ws ... */
}
export type ServiceKey = keyof ServiceMap;
export type DepsOf<I extends readonly ServiceKey[]> = Pick<ServiceMap, I[number]>;

/** 插件上下文：只有 app + env。服务认领靠返回值，依赖靠 deps 注入——内核面无 register/get */
export interface PluginContext {
  app: FastifyInstance; // server/desktop：将 listen 的实例；worker：不 listen 的容器
  env: ServerEnv;
}

/** 服务型插件：name 即 ctx key，至多认领一个服务 */
export interface ServicePluginDef<K extends ServiceKey, Deps> {
  name: K;
  inject?: readonly ServiceKey[];
  enabled?: (env: ServerEnv) => boolean; // 缺省 true；payments/jobs 类开关收编于此
  apply(deps: Deps, ctx: PluginContext): {
    service: ServiceMap[K];
    dispose?: () => void | Promise<void>;
  };
}
/** 挂载型插件：贡献路由/基础设施（cors、multipart、health…），不占 key 表 */
export interface MountPluginDef<Deps> {
  name: string; // 约定 "<域>:<名>"，如 "http:cors"
  inject?: readonly ServiceKey[];
  enabled?: (env: ServerEnv) => boolean;
  apply(deps: Deps, ctx: PluginContext): void | (() => void) | Promise<void>;
}
export type PluginDefinition =
  | ServicePluginDef<ServiceKey, Partial<ServiceMap>>
  | MountPluginDef<Partial<ServiceMap>>;

/** 类型推断恒等函数：inject 字面量 → deps 精确形状；name → 返回值按 ServiceMap[K] 校验 */
export function definePlugin<K extends ServiceKey, const I extends readonly ServiceKey[]>(
  def: ServicePluginDef<K, DepsOf<I>>,
): ServicePluginDef<K, DepsOf<I>>;
export function definePlugin<const I extends readonly ServiceKey[]>(
  def: MountPluginDef<DepsOf<I>>,
): MountPluginDef<DepsOf<I>>;

export interface ComposeOptions {
  env: ServerEnv;
  overrides?: Partial<ServiceMap>; // 命中 key 的工厂跳过执行（测试替身语义）
}

export interface MountNode {
  plugin: string;
  status: "mounted" | "disabled"; // enabled(env) 判定快照
  provides?: ServiceKey;
  inject: readonly ServiceKey[];
}

export interface ComposedApp {
  app: FastifyInstance;
  services: Readonly<ServiceMap>; // worker / 单测直取服务，不经 HTTP
  dump(): MountNode[];
  dispose(): Promise<void>; // app.close()（内部 onClose 逆序回卷）+ 幂等
}

export function composePlugins(
  plugins: readonly PluginDefinition[],
  options: ComposeOptions,
): ComposedApp;
```

### 3.3 fail loud 语义（boot 期全部同步抛出）

依赖环（avvio 报错含路径）；缺失依赖（翻译 avvio 报错：指名 inject 它的插件与被 enabled 关闭的提供者）；重复 `name`；服务插件返回值与 `ServiceMap[name]` 类型不符（编译期拦截）。

### 3.4 已知取舍（接受的疼）

无 optional inject——generate 路由对 jobService 的可选消费改由「同 enabled 谓词的兄弟挂载插件」表达；多服务 feature 拆多个插件定义；全量 eager 构造（靠 profile 分树控制 worker 不挂 HTTP-only 插件）；`definePlugin` 双 overload 的 TS 报错可读性一般。

- **手填 + 可选拉取**：实例的 `models` 数组是单一事实源；添加实例时手填，提供「从 /models 拉取」按钮（openai-compatible / gemini 支持列表接口），拉回后可编辑。

### 4.5 Checkpoint 结论（影响存储支）

- 用途：agent 暂停/恢复 + human-in-the-loop 向用户提问的中断恢复。
- **v1：进程内 `MemorySaver`**——run 进行中进程必然存活，中断恢复不落库；对话/事件历史由 agentPersistence 落库完整可查。跨重启语义 = run 标记中断、Task 历史保留、「继续」发起新 Run（与 Claude Code 关终端后重开一致）。参考依据：Codex 的 ask-user 暂停同样是协议层内存状态，跨重启靠 JSONL 重放历史而非恢复执行中状态。
- **v2：PostgresSaver + PGlite**（桌面）/ Supabase PG（服务端）——仅当出现「桌面升级不停 run」「无人值守长任务」需求时启用（PGlite-socket 让 pg 驱动直连，PostgresSaver 原样可用）。

## 5. 存储缝接口 ✅

> 决策过程：Design It Twice——4 个并行子代理分别以「极简 SQL / Repository-per-feature / Kysely 构建器 / 事件日志溯源」视角设计后综合。

### 5.1 方案：B 的消费面 + C 的实现基底 + A 的 shim + D 的划分原则

- **消费面（per-feature repository）**：feature 只见自己的窄 repository 接口——方法名对应**业务动词**而非表操作，≤8 方法，接口住在 feature 目录；防薄透传判据：方法 = 服务端一次数据访问单元（含 join/RPC/错误翻译），`Database` 行类型不得泄漏。
- **实现基底（Kysely）**：`kysely`（运行时零依赖）+ `kysely-codegen` 从活库**单向生成**行类型，CI 重跑生成 + diff 门禁——与 `supabase gen types` 同构，把「迁移 SQL 唯一事实源」的结构性保证从纪律升级为门禁。Drizzle 被否（TS-schema-push 模式制造第二事实源）。Kysely 自带 `sql` tagged template 作为裸 SQL 逃生口（RPC、复杂查询）。
- **RLS 跨驱动（事实核验）**：RLS 是 Postgres 引擎层行为，直连 pg 不绕过——事务内 `SET LOCAL ROLE authenticated` + `SET LOCAL request.jwt.claims` 即与 PostgREST 等价；PGlite 原生支持 RLS（陷阱：其默认用户 postgres 是 superuser 天然 BYPASSRLS，故驱动封装连接、永不裸露）。
- **信任边界修补**：`withUserRls` 用 branded type 强制传入**验签后的 `AuthenticatedUser`**（含 accessToken），禁止裸 `{id}`——claims 只能来自已验签身份，把「服务端注入 claims」的信任边界钉在类型上。
- **启动自检**：`createSupabaseStorage` 启动期校验连接角色非表 owner 且为 authenticated 成员——self-host 下 owner 绕过 RLS 的静默陷阱 fail loud。
- **local 驱动 shim**（≈100 行 SQL，migrate() 先于迁移重放）：建 `anon/authenticated/service_role` 角色 → `auth` schema + `uid()`（读 claims GUC）→ 装 pgcrypto/moddatetime 到 `extensions` → `storage.buckets/objects` 桩表 + `foldername()` 桩函数（让既有 storage policy 逐字重放不报错）。之后 `supabase/migrations/*.sql` **逐字重放**，无注解无转译无第二套迁移史。
- **blob 统一**：`put/get/delete/publicUrl`（bucket 降级为逻辑命名空间：supabase storage bucket ↔ 桌面本地目录 + sidecar loopback 路由）；v1 四桶全 public，签名 URL 不进接口。
- **日志划分原则（D）**：消息/Run 事件/产物引用天然 append-only 即可，**不建通用 FactLog 缝**（自省：若桌面同步改整库复制则该缝退化为 insert-only repository）；可变实体（供应商实例/设置/项目元数据）走 repository CRUD。

### 5.2 接口签名

```ts
export interface BlobStore {
  put(bucket: BlobBucket, path: string, body: Buffer, mime: string): Promise<void>;
  get(bucket: BlobBucket, path: string): Promise<Buffer>;
  delete(bucket: BlobBucket, path: string): Promise<void>;
  publicUrl(bucket: BlobBucket, path: string): string;
}
type BlobBucket = "project-assets" | "user-avatars" | "brand-kit" /* 封闭联合 */;

export interface StorageAdapter {
  /** 各 feature repository 集，逐个随 Phase 3 迁移补齐；首个试点 modelProviders */
  repos: FeatureRepositories;
  blob: BlobStore;
  /** RLS 事务：BEGIN; SET LOCAL ROLE authenticated; SET LOCAL request.jwt.claims=…; COMMIT */
  withUserRls<T>(user: VerifiedUser, fn: (tx: RepositoryTx) => Promise<T>): Promise<T>;
  /** 服务角色事务：worker/executor 侧 */
  withServiceTx<T>(fn: (tx: RepositoryTx) => Promise<T>): Promise<T>;
  migrate(): Promise<void>; // shim + supabase/migrations 逐字重放（幂等，含 SHA-256 账本）
}

export function createSupabaseStorage(deps: { dbUrl: string; /* … */ }): StorageAdapter;
export function createLocalStorage(deps: { dataDir: string; blobRoot: string }): StorageAdapter; // D1 落地
```

### 5.3 节奏（两设计与现状约束的共识）

1. **现在**：只落缝契约（零运行时依赖）+ **modelProviders（BYOK）做首个 repository 试点**（greenfield、凭证红线敏感、双驱动测试就地建立）。
2. **Phase 3**：存量 129 处 `.from()`（24 文件）跟随 feature 插件化逐个迁移，每迁移一个 feature 补一个 repository + 契约测试；禁止大爆炸。
3. **D1（桌面）**：才写 `createLocalStorage`（PGlite 驱动）；此前不写无消费者的实现。
4. 队列缝：桌面 = 进程内队列（复用 registerExecutor 契约），服务端 = PGMQ——queue 接口随能力节点支设计（§6）。

## 6. 沙箱与能力节点 ✅

### 6.1 沙箱执行后端选型（开源调研结论）

**主后端：`srt`（@anthropic-ai/sandbox-runtime，Anthropic 开源，Apache-2.0）**

| 维度 | 结论 |
| --- | --- |
| 平台覆盖 | 三平台全：macOS Seatbelt（sandbox-exec）/ Linux bubblewrap / Windows 专用 `srt-sandbox` 本地账户 + WFP（Windows Filtering Platform）出站围栏 + 工作树 per-session ACE |
| 网络控制 | **代理级域名白/黑名单**（HTTP proxy + SOCKS5）——超出 dsh/Codex 基础能力，是 agent 安全的关键件 |
| 形态 | npm 库 + CLI 双形态，与本仓库 Node 栈同构；Claude Code 同款生产验证；活跃迭代（v0.0.76，2026-09-10） |
| 风险 | Beta Research Preview（API/配置格式可能演进）→ 由自建 Sandbox 缝隔离消化；**Windows 档为 alpha**（装机需管理员：WFP 过滤器 + 专用账户，文档化）；6.1.2 分层阶梯兜底 |
| 兜底语义（借鉴 dsh sandbox-local） | **fail-closed**：无可用 runner 绝不静默裸奔执行；enforcement 等级报告（`full`/`partial`）+ denial signatures，区分「沙箱坏了」与「命令被拒」 |

- 备选落选原因：完全自研（网络白名单代理是最重自建件，重复造 srt 已有轮子）；Codex `codex-linux-sandbox` 二进制复用（仅 Linux，碎片化）；容器/microVM（E2B 等，与「桌面直跑用户项目文件夹」的 Work 形态冲突，云端形态后置再评估）。
- 版本与成熟度（2026-09-15 复核）：v0.0.76；**Windows 为 alpha 档**——随包 `srt-win.exe` helper（无额外依赖），安装需管理员（建 `srt-sandbox` 专用账户，密码 DPAPI 加密存 HKLM；幂等重装会轮换密码并 reconciling 过滤器集）。

### 6.1.1 档位定性（2026-09-15 评估采纳）

**SRT 属「客户端护栏」档，与其他所有沙箱产品不同赛道**：Docker/gVisor/Firecracker 系（E2B/microsandbox/Kata）回答的是「把不可信代码放到别的地方跑」（服务端平台）；SRT 回答的是「让 agent 在**我的机器**上安全地干活」（客户端护栏）。定性决定全部下游判断：

- **对抗目标**：SRT 对抗的是「失控的 agent」，不是「决心攻击你的对手」——共享宿主内核，内核漏洞（Dirty Pipe 类）在射程内；microVM 档这类整体出局，这是档位差的本体。
- **失败模式不对称**：SRT 败于**配置错误**（静默、高频、忘一条 deny 就把 `~/.ssh`/`~/.aws`/浏览器 cookie 放进射程——fail-closed 与缝隔离恰治此面）；VM 败于**逃逸**（罕见、高成本、不可预防，但 VM 内本无用户密钥）。
- **本产品的主场**：agent loop 的会话内数百次短命令（grep/测试/改文件）——本机 exec 毫秒级包装、文件即真实工作树、代码不出本机；SRT 在 macOS（agent CLI 主市场）是**唯一原生选项**。
- **毕业信号（升档 microVM/云沙箱）**：要执行的不是自家 agent 的产物（第三方仓库/恶意样本）；或单机并发会话开始互踩（需要密度/镜像故事）。云端形态届时分流，v1 不做。

### 6.1.2 Windows 支持矩阵修正与分层阶梯

**修正**：外部评估曾称「SRT 无 Windows 原生支持（仅 macOS/Linux，全行业 Windows 空白）」——**已过时**。当前 README（v0.0.76）实证 Windows 原生路径存在（alpha）：专用账户 + WFP 出站围栏 + per-session ACE + 代理通道，与 macOS/Linux 同一套 `SandboxManager.initialize()`/CLI 语义。⇒ 本产品 Windows 走 **srt native**（跟随先例，非自研开荒）；行业对照（Claude Code/Codex/Trae/Cursor/Gemini CLI 在 Windows 上集体退化为「审批制，无隔离」）仍是反面教材：**别人的降级是静默的，我们的必须是响亮的**。

| 阶梯 | 条件 | 形态 |
| --- | --- | --- |
| **L1** | Windows + 管理员可装机 | **srt native（alpha）**：`srt-win` 初始化（WFP 围栏 + 专用账户），装机流程文档化提权步骤 |
| **L2** | 检测到 WSL2 | bubblewrap 档（WSL2 = 真 Linux 内核轻 VM，边界反而比共享账户档更硬）——**必须焊缝**：`wsl.conf` `[automount] enabled=false`、`[interop] enabled=false`、`appendWindowsPath=false`、repo 放 ext4（/mnt/c 走 9P 慢到不可用）、userns 受限时 fail-closed 照搬 |
| **L3** | 无 WSL2 有 Docker Desktop | 容器档（Hyper-V 直出，比 mac Docker 更硬） |
| **L4** | 皆无 | 原生模式：**红幅明示「本模式无隔离，仅审批把关」** + 默认收紧（LOLBins 名单拒执行、PowerShell `-EncodedCommand` 类高熵参数默认拒）——行业 L3 全是静默的，这里是本产品的净增量点 |

### 6.1.3 三条补强（纳入 Sandbox 缝设计，优先级序）

1. **secrets 出 $HOME**：ssh-agent 隔离/只读注入——让「配置错误」的默认损失降级（SRT 真正的软肋是配置错误的爆炸半径，不是逃逸）。
2. **Linux 回退链 fail-closed**：unprivileged userns 被发行版收紧（Ubuntu 24.04 AppArmor、Debian sysctl 默认）时 bwrap 不可用 → 明确报错，**绝不静默裸跑**——静默降级是全行业反面教材（见 6.1.2 L4 对照）。
3. **代理作为唯一 DNS 出口**：堵 DoH/硬编码 resolver 这个域名白名单最大的洞。macOS 无 netns（结构性弱项，只能 Seatbelt 全禁网 + 代理 env 约定）；Linux 用 `--unshare-net` 让代理成为唯一出口（做得硬）。诚实标注：egress 失守后爆炸半径仍是「本机用户账户」，与云沙箱「临时数据」不对等——这是档位属性，不是实现缺陷。

### 6.2 双层权限模型（§2.3 已定）落地

- **Sandbox 缝**（自建接口，srt 为首个 adapter）：`execute(command, policy) → { outcome, enforcement, denials }`；policy 由产品权限模式（plan/ask/auto-edit/full-access）映射为沙箱档 + 文件系统范围（可写根 = 项目文件夹）+ 网络白名单。
- **网络默认策略**：`plan`/`ask`/`auto-edit` 档默认 deny-all 外网 + 预置常用域白名单（npm/pypi registry、GitHub 等）+ 审批门动态放行（弹窗显示目标域名）；`full-access` 不限。
- **审批门**：文件编辑（ask 档）/ 未白名单网络 / 危险命令三类同意门；一次性行内提权（记住本次 Task 内选择）。

### 6.3 能力节点（Worker）v1 范围

- **两态执行**：桌面 = sidecar 进程内本地 Worker（沙箱执行器 + 图/视频生成 executor 同进程，BYOK API 调用本地直发）；服务端 = 现有 PGMQ 队列路径不变。
- **节点注册协议（注册/心跳/能力清单/按能力路由）后置 v2**——等独立 Worker 容器（自部署横向扩容）真实出现再做，避免为无消费者的抽象铺路。
- **computer-use（本机 GUI 操控）**：v1 不做；北极星是终端/文件闭环，GUI 操控平台差异与安全面最大，待 D5 后按需评估。

## 7. 桌面壳 ✅（继承多端计划，随新决策修订）

- **Tauri 2**：系统 WebView（WKWebView / WebView2 / WebKitGTK）+ Rust 薄层（窗口/托盘/自更新/深链/Keychain/OS 文件夹选择对话框）；业务一律在 sidecar——桌面与自部署行为一致。
- **Sidecar 方案 A**：Node SEA 或 `bun build --compile` 把同一服务端打成单文件可执行，随 Tauri 资源分发；常驻内存预算 80–150 MB。
- **桌面数据布局**：`~/.kenfutwork/`（PGlite 数据库 + blob 目录；2026-09-06 命名拍板，原 `~/.kenfutwork/` 废弃）；Keychain 存供应商 Key；项目 = 用户选择的本地文件夹（沙箱可写根）。
- **认证**：local-trust（loopback 免登录，单用户）；服务端形态不变（Supabase JWT）。免登录指桌面 UI 体验——Tauri 壳自动持有本地 pairing token 附加到请求，HTTP/WS 仍校验 token + Origin，防其他本机进程劫持；浏览器/移动连接走 QR 配对。
- **内存预算**：桌面空闲 RSS < 400 MB；dev 模式打印挂载树与各进程 RSS，超阈值告警。
- **自更新**：Tauri updater；sidecar 与壳版本强同步（单包发布）。
