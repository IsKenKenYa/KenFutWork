# flow P7 深度收编评估（futureFlow → 主仓单进程）

> **角色**：方案稿——《[flow 插件集成规划](./flow插件集成规划.md)》§6 里 P7「（远期）深度收编评估 · 届时另立方案」所指的那份方案。**只做评估与前置条件定义，不做实施**；决策结论拍板后仍以《[改造计划](../方案设计/改造计划.md)》§6 为准。
> **结论摘要**：**建议继续暂缓 C 形态**。B 形态（iframe 内嵌）已经跑通且隔离性更好，C 的收益集中在「少一套 Node 进程与一套版本」，代价是拆掉两条主仓硬纪律（迁移单源、插件形状）并长期承担双技术栈的合并成本。**触发条件见 §3，目前有 1 条不满足**。
> **现状快照**：2026-10-13 工作区实测（`flow/` 子模块 HEAD `b62fcbe`，上游 `github.com/future73807/futureFlow`）。

## 1. 三种合并形态的现状

| 形态 | 内容 | 现状 | 证据 |
| --- | --- | --- | --- |
| **A. 子模块独立运行** | 双栈各自跑，零耦合；指针跟随上游 | **已落地** | 根级 `flow/` 子模块；`pnpm-workspace.yaml` 不含 flow（flow 自带 workspace） |
| **B. iframe 内嵌** | 主仓加 flow 模式骨架 + 上游宿主适配层 `ff-embed/v1`；NestJS 网关与本地 Dify 栈作为**独立子系统**保留 | **已落地（P0–P6 全绿）** | 主仓 `apps/web/.../host/FlowSurface.tsx`；上游 `frontend`/`gateway` 未折叠；《日志》一百六十 记录「壳内 Dify 画布完整加载」 |
| **C. 深度代码收编** | frontend 折叠进 `apps/web`、网关改写为 Fastify `features/flow/`、TypeORM 迁移翻译进 `supabase/migrations` | **未启动** | 主仓无 flow 域服务/路由；`supabase/migrations` 无 flow 表；flow 侧 36 个迁移仍在 `gateway/src/database/migrations` |

## 2. C 形态的工作分解与成本量级

### 2.1 前端折叠（`flow/frontend` → `apps/web`）

| 项 | 现状 | 收编后 | 成本/风险 |
| --- | --- | --- | --- |
| 框架 | React 18 + Semi UI + **Rsbuild** | React 19 + Base UI + **Next 16 App Router** | **高**：组件库与构建器全换；Semi 组件无等价物需逐个重写 |
| 版本冲突 | 靠 iframe 天然隔离 | 同一 React 树内共存 | **高**：React 18/19 不能同树共存，收编即等于「重写」而非「搬迁」 |
| 画布 | FlowGram（`/canvas/:id` 自包含视图） | 需在 Next 路由下重挂 | 中：FlowGram 是独立依赖，可在 React 19 下复用，但 Semi 依赖需剥离 |

**结论**：前端折叠的真实成本不是「搬文件」，是**重写一个可视化编排前端**。这一项单独就足以让 C 的性价比不成立。

### 2.2 网关折叠（`flow/gateway` NestJS → Fastify `features/flow/`）

| 项 | 现状 | 收编后 | 成本/风险 |
| --- | --- | --- | --- |
| 框架 | NestJS（DI/装饰器/模块） | Fastify + 主仓插件形状（Service Definition / Provider / Consumer） | 中高：NestJS 的 DI 与主仓 kernel 是两套装配模型，需逐模块改写 |
| 体量 | DSL 转换 3286 行、Dify Console 集成 1732 行、双模鉴权/扣费三段事务 | 原样迁移（业务逻辑可复用） | 中：逻辑可搬，但**必须落在适配器内**（`DEC-13` 的兼容硬编码不得渗出） |
| 计费 | 自带 balance + 三段事务 | 主仓本期**免账户无计费**（`DEC-20` 已退役 credits/平台池） | 低收益：这段在主仓当前形态下是死代码 |

**结论**：网关折叠技术可行、成本可控，但收益主要是「少一个 Node 进程」；而**计费部分在主仓当前形态下反而是负担**。

### 2.3 迁移翻译（36 个 TypeORM 迁移 → `supabase/migrations`）

| 项 | 说明 | 风险 |
| --- | --- | --- |
| 体量 | `gateway/src/database/migrations` 共 **36 个** TypeORM 迁移 | 中 |
| 语义 | TypeORM 的 `up/down` + 装饰器 schema → 原生 SQL | **高**：主仓 `supabase/migrations` 是**唯一 Schema 迁移源**（AGENTS.md 硬约束），flow 表并入后，「flow 独立升级」与「主仓迁移单源」会互相拉扯 |
| 数据 | 已有用户数据卷（`down` 默认保留） | **高**：迁移源切换涉及存量数据的一次性搬迁与回滚方案 |

**结论**：这是 C 里**唯一不可逆**的部分。一旦并入，flow 的表结构就不能再随上游自由演进了。

## 3. 触发条件（满足才建议启动 C）

| # | 条件 | 判定标准 | 当前状态 |
| --- | --- | --- | --- |
| 1 | **上游进入稳定期** | 连续 3 个月无 force-push、无破坏性 schema 变更 | **不满足**：上游 2026-09-17 有 force-push 实测记录（规划 §8 风险 1）；MVP 冲刺期 |
| 2 | **B 形态全链验收通过** | 内嵌/独立双形态各自跑通 + `ff-embed/v1` 契约稳定（无破坏性变更） | 部分满足：本地壳内画布已完整加载；WSL2 真机路径已于 2026-10-13 验收（引擎栈 9/9 容器 → 停止回收，见《日志》一百八十七） |
| 3 | **主仓确有「单进程」刚需** | 出现 B 形态无法解决的实际问题（如：安装包体积、启动进程数、离线场景） | 不满足：当前无此类诉求；桌面形态已用「插件 + 引擎按需下载」解决体积问题 |
| 4 | **前端框架收敛** | 上游 frontend 迁到 React 19，或主仓接受长期维护 React 18/19 双栈 | 不满足：上游 React 18 + Semi UI |

**四条里 3 条不满足**，因此本轮不启动 C 是正确的。

## 4. 若未来启动：建议的实施顺序

1. **先做 §2.3（迁移翻译）的可行性预研**，不做实施——因为它不可逆，要先拿到「存量数据搬迁 + 回滚」的方案与演练结果，再谈其它两块；
2. **网关折叠先于前端折叠**：网关是纯逻辑迁移、风险可测；前端折叠等于重写，应最后做（甚至可以考虑永远不做——B 形态的 iframe 隔离反而更安全）；
3. 每一步保持「A/B 形态仍可用」——即收编过程中不破坏子模块路径，直到 C 完全就位再摘除。

## 5. 与主仓纪律的冲突点（必须显式拍板才可动）

| 纪律 | 出处 | C 形态的冲突 |
| --- | --- | --- |
| 迁移单源 | AGENTS.md「`supabase/migrations/` 是唯一数据库 Schema 迁移源」 | flow 表并入后，flow 不能再独立演进 schema |
| 插件形状 | AGENTS.md「没有特权核心」「能力缝三元组完整才算完整」 | 网关折叠必须按 Service Definition + Provider + Consumer 组织，不能只是「塞一个 NestJS 应用进来」 |
| references 例外 | AGENTS.md「`flow/` 是待合并子系统，不受 references 禁止复制约束」 | C 完成后该例外条款应同步修订 |
| 双版本隔离 | 规划 §5 B 形态论证 | 收编即放弃隔离，需接受 Semi UI 与 Base UI 共存或重写 |

## 6. 开放问题

1. 上游若长期停留在 React 18 + Semi UI，前端折叠是否**永久放弃**？（建议：是，B 形态足够）
2. 36 个 TypeORM 迁移里，有多少在主仓形态下是**死表**（计费/多租户/RBAC 相关，`DEC-20` 已退役）？—— 先做这个盘点能把 §2.3 的真实体量砍掉一截。
3. C 形态是否只做「网关 + 引擎」而**不做前端**（即 B 与 C 的混合形态）？—— 这可能是性价比最高的中间解，建议作为下次评估的首选议题。
