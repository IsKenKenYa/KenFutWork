> 角色：**调研 + 方案规划**（参考级，非权威）。结论拍板后落地写入《改造计划》§4.13 台账。
> 状态：待拍板（2026-09-18 首次成稿）。
> 需求来源：2026-09-18 用户提出的要求（§1.1）。所有「实测」结论均在本机代码上核对过，附文件与行号；模型与体积数据来自官方仓库/官方文档，来源见 §3.6。

## 0. 结论速览

| 决策点 | 结论 |
| --- | --- |
| 交付形态 | **内建插件**：`apps/server/src/features/voice/plugin.ts` + `profiles/server.ts` 清单一行 |
| 默认开启 | **不写 `enabled` 门** —— 内核是 `plugin.enabled?.(env) ?? true`（`apps/server/src/kernel/compose.ts:58`），无门即默认挂载 |
| 是否走插件市场 | **不走**。市场插件（第三方 bundle）的能力面给不了这个功能，见 §1.3 |
| 功能模式 | 两套都做：**A 只转文本（默认档）** / **B 完整回路「听 → 想 → 说」** |
| 默认档由谁定 | **性能检测**（§6）给出推荐档与实测代价；检测不删功能，只有硬缺失才置灰 |
| 三段模型 | 听 / 想 / 说 每段独立可调，候选含「在线（默认，零下载）」与「离线（选中才下载）」 |
| 「想」段默认 | **在线**（当前 run 的对话模型）；离线 Qwen3-4B 是降级档（CPU 上补一条需求要 10–25 秒） |
| 输入框交互 | 删除麦克风按钮，**按住输入框即录音**（§7） |
| 本地运行时 | `sherpa-onnx-node`（CPU，Windows x64 有预编译包，无需 Python/PyTorch） |

## 1. 需求与项目侧约束

### 1.1 需求（用户口径，按出现顺序）

1. 本地接入语音能力，位置在输入框的麦克风处。
2. 识别语音 → 理解意图 → **转换成专业的完整需求**。
3. 支持连续对话；对话框支持**按住鼠标**代替点击语音按钮，按住不松开即录音，语音按钮去掉。
4. 两套方案都要做：一套「听 → 想 → 说」完整回路（理解需求 + 执行），一套语音只转文本；**默认只转文本**，可在设置里调整。
5. 转文本这一步可以用精度更高的模型。
6. 听 / 想 / 说每一步的模型都可调整，模型分 CPU 与 GPU 版本，可自由切换与混搭；「想」可选离线模型（**选中之后才下载**）或默认的在线模型。
7. 以**插件**形态交付，且**默认开启**。

### 1.2 「默认开启」的准确机制（实测）

- 插件定义是 `{ name, inject, enabled?, apply, mounted? }`（`apps/server/src/kernel/types.ts:264-275`）。
- 装配时过滤：`const active = plugins.filter((plugin) => plugin.enabled?.(env) ?? true)`（`apps/server/src/kernel/compose.ts:58`）——**判定缺省为 true**。
- 判定为 false 的插件会在启动日志留痕（`apps/server/src/kernel/compose.ts:60-66`），这是内核既有的「配置 fail loud 可见性面」。
- 结论：语音插件进 profile 清单、**不写 `enabled` 判定**，即默认开启。用户侧的开关是**功能模式**（只转文本 / 完整回路），不是插件启停。

### 1.3 为什么不做成市场插件（实测硬边界）

市场插件（第三方 bundle）跑在受限能力面上，四条硬边界使它无法承接语音助手：

1. **能力面只有四项**：`tools` / `systemPrompt` / `routes` / `ui`（`apps/server/src/features/plugins/capability-binding.ts:34,72,77,82`），其余能力显式拒绝并给出理由——没有 DB、密钥、设置通道，插件重启即失忆。
2. **门禁禁止直连系统**：`child_process`、`worker_threads`、`node:vm`、`node:cluster`、`node:fs` 等字面 import 一律判 blocker（`apps/server/src/features/plugins/module-scan.ts:32-44`）。
3. **bundle 不能带 npm 依赖**：GitHub 来源跳过 `node_modules`，只收文本白名单（`.json/.js/.mjs/.cjs/.yml/.md/.html/.css/.svg`，单文件 512KB；`apps/server/src/features/plugins/bundle-source.ts:49-80`）。
4. **安装 / 卸载 / 停用都要管理员**（`apps/server/src/http/plugins.ts:76,124,190,331,352`），与「默认开启」直接冲突。

语音助手要**加载原生 onnx 运行时、读模型文件、注册 provider 缝、写设置**——四项能力都给不了，因此只能是内建插件。第三方插件调研的既有结论（`DEC-8`）不受影响。

### 1.4 输入框侧现状与判定（实测）

- 全仓**没有任何语音实现**：无 `getUserMedia` / `MediaRecorder` / `SpeechRecognition` / ASR 端点；只有两个点不动的占位麦克风按钮：
  - 追问输入框：`apps/web/src/components/workbench/workbench.tsx:2714-2720`
  - 空态输入框：`apps/web/src/components/workbench/workbench.tsx:3019-3025`
  - 两者都是 `<button title="语音（即将上线）">`，无 `onClick`。
- Design 画布助手的输入框（`apps/web/src/components/chat-input.tsx:331-431`）**连麦克风都没有**，工具行是「添加图片 / 模型选择 / 图像模型偏好 / 发送」。
- 用户提供的参考图是另一个产品的输入框（工具行是表情/方盒/文件夹/剪刀那排），与本源码无关。**判定：参考图只取交互（按住说话），不重排现有工具行**——现有输入区的尺寸与控件口径已定稿在《改造计划》§4.13 第十五轮，不做无谓改动。
- 合同输入框的三处落点（追问 / 空态 / 画布助手）共用同一个手势 hook 与状态条。

## 2. 能力缝（三元组）

按《改造计划》§4.4 的硬规则：一个可替换能力 = Service Definition + Service Provider + Consumer，半个缝不合入。本插件贡献三条能力（听 / 说 / VAD）与一个 Consumer（HTTP 路由 + 前端输入框）。

### 2.1 Definition

`apps/server/src/features/voice/types.ts`：

- `VoiceTranscriber`：`transcribe(wav: Uint8Array, opts: { language?; signal? }) => Promise<{ text: string }>`。
- `VoiceSynthesizer`：`synthesize(text: string, opts: { voice?; signal? }) => Promise<{ audio: Uint8Array; mimeType: string }>`。
- `VoiceActivityDetector`：`segment(pcm: Int16Array) => { segments: Array<[number, number]> }`（离线切句用；常驻监听不做，见 §8）。
- 三个接口共同的 `ready(): Promise<{ ok: boolean; reason?: string }>`，供检测与 fail loud 使用。

### 2.2 Providers

| Provider | 文件 | 承载 | 依赖 |
| --- | --- | --- | --- |
| 内置离线 | `features/voice/providers/sherpa.ts` | 听 / 说 / VAD | `sherpa-onnx-node`（CPU；Windows x64 有预编译包；Node ≥18） |
| OpenAI 兼容端点 | `features/voice/providers/openai-audio.ts` | 听 / 说 | 复用 BYOK 供应商实例的 `baseUrl` / 凭证 / 自定义头 |

- 内置 provider **懒加载**：首次调用才载入模型；模型位于 `~/.kenfutwork/models/<模型 id>/`。
- OpenAI 兼容 provider 就是既有「本地端点」路子：`baseUrl` 可填 `http://127.0.0.1:PORT/v1`，协议 `openai-compatible`（先例见 `scripts/本地模型替身.mjs:1-14` 的用法说明；聊天适配器同样支持 `baseURL`，`apps/server/src/providers/openai-compatible/index.ts:13-20`）。**在线档因此不需要新协议，也不需要新配置通道**。
- 注册表沿用既有形状：`apps/server/src/providers/resolve.ts:29-96` 的 `CHAT_ADAPTERS` / `IMAGE_ADAPTERS` / `VIDEO_ADAPTERS` 与 `resolveInstance*` 的 fail loud 写法，语音加同形的 `AUDIO_ADAPTERS`。

### 2.3 Consumer（HTTP）

`apps/server/src/http/voice.ts`，在插件的 `mounted()` 里注册（路由注册属于「消费其他插件服务」的跨服务接线，按 §4.10 与 `kernel/types.ts:265-275` 的约定放 `mounted`，`apply` 只注册自己的服务；不改 `app.ts` / `worker.ts`）：

| 路由 | 用途 |
| --- | --- |
| `POST /api/voice/transcribe` | multipart 音频（16kHz 单声道 WAV）→ `{ text }` |
| `POST /api/voice/refine` | 转写文本 + 最近 N 条会话消息 → `{ prompt }`（完整需求） |
| `POST /api/voice/speak` | 文本 → 音频（语音回复） |
| `GET/POST/DELETE /api/voice/models` | 模型目录 / 按需下载 / 删除 |
| `POST /api/voice/diagnose` | 性能检测报告 |

音频传输沿用既有上传面：multipart + `@fastify/multipart`。注意全局体积上限目前是 10MB（`apps/server/src/app.ts:36`），上传 MIME 白名单目前只收图片（`apps/server/src/http/uploads.ts:16-20,49-55`）——语音走**独立的路由与独立白名单**（`audio/wav` 等），不复用图片上传通道。

### 2.4 契约与错误码

- `packages/shared/src/provider-contracts.ts:20` 的 `modelCapabilitySchema` 目前是 `chat | image | video`，且 `packages/shared/src/provider-contracts.test.ts:33` **显式断言 `audio` 被拒**。要加音频能力必须改契约并**有意**改掉这条断言（改为断言 `audio` 通过、未知能力仍拒）。
- 协议封闭集合（`provider-contracts.ts:9-18`）**不动**：在线走的仍是 `openai-compatible`。
- 错误码复用现有封闭枚举（`packages/shared/src/http.ts:450`）：未装/不可用 → `service_unavailable`（503）；音频非法或超限 → `invalid_input`。**不要新增未登记的码**——历史事故：新码不在枚举里时响应会退化成 ZodError 转储，前端只看到一段乱码 JSON（该枚举注释里已记录）。
- 副作用与幂等：转写与改写都**不落库、不动余额、不写用量**，按《AGENTS.md》「持久副作用与幂等性」标记为 `unsafe`（HTTP 层不自动重试）；模型下载是文件系统副作用，但可重放（校验和不匹配即失败且不留半截文件）。

## 3. 选型与已核实数据

三段是三类问题，不找单个 omni 模型：MiniMind-O 这类 0.1B omni 无独立转写模式（A2A 是语音进语音出），而 7B+ 的 omni（Qwen2.5-Omni / MiniCPM-o / GLM-4-Voice / Moshi）在 CPU 上不可能流畅。

### 3.1 听（ASR）

| 候选 | 体积 | 说明 |
| --- | --- | --- |
| **SenseVoiceSmall int8**（sherpa-onnx 版，2024-07-17） | **228MB**（fp32 894MB） | 普通话 / 粤语 / 英 / 日 / 韩；`use_itn=1` 输出带标点与逆文本规整；非自回归，官方口径「比 Whisper-Large 快 15 倍」 |
| SenseVoiceSmall int8（2025-09-09 版） | 226MB | 用 21.8k 小时粤语微调，但**不支持标点** → 不选 |
| faster-whisper large-v3-turbo | 约为 large-v3 的一半 | 中文更稳，CTranslate2 int8；CPU 上比 SenseVoice 慢 |
| whisper.cpp 各档内存占用 | tiny 273MB / base 388MB / small 852MB / medium 2.1GB / large 3.9GB | 纯 CPU 可跑；`whisper-server` 自称 OAI-like API |

### 3.2 想（意图理解 + 补成完整需求）

| 档 | 选型 | 体积 | 代价 |
| --- | --- | --- | --- |
| **默认（在线）** | 当前 run 的对话模型（BYOK） | 0 | 首 token 亚秒级；能读上下文（「刚才那个按钮」这类指代只有带上下文的模型补得出） |
| 离线降级 | Qwen3-4B-Instruct-2507 GGUF Q4_K_M | 2.5GB | CPU 上按内存带宽推算约 **10–20 tok/s** → 补一条 150–250 token 的需求要 **10–25 秒** |
| 离线（更小/更大） | Qwen3-1.7B（1.4GB）/ Qwen3-30B-A3B（19GB，稀疏 MoE 只激活 3B，但要 32G 内存） | — | 1.7B 更快更笨；30B-A3B 是 CPU 上「更大但不太慢」的唯一档 |

注意：10–20 tok/s 是**按内存带宽推算的量级，不是实测**（第三方实测数字未取到可信来源）。§6 的检测负责量准并写回本节。

### 3.3 说（TTS）

| 候选 | 体积 | 许可 |
| --- | --- | --- |
| **Kokoro-82M** | 82M 参数，CPU 实时 | Apache-2.0（含权重） |
| `sherpa-onnx` 的 zh 系列：`vits-zh-ll`（5 音色）/ `vits-zh-hf-fanchen-C`（187 音色）/ `aishell3`（174 音色）/ `matcha-icefall-zh-baker` | 几十~几百 MB | 各模型卡为准 |
| Piper | 轻 | MIT |

### 3.4 三段混搭：CPU / GPU / 远端

- 内置路径是 **CPU**（onnxruntime CPU EP）；**GPU 走外部端点**（Speaches 支持 CPU/GPU；faster-whisper 的 CUDA 版；或直接指云端）。
- 检测到 NVIDIA GPU 时（`nvidia-smi` 尽力探测）在设置页提示「可接 GPU 服务」，探测不到不影响功能。
- 「运行位置」是每个候选卡片上的一个标注（本机 CPU / 本机 GPU / 远端），不是另一套配置通道。

### 3.5 业界做法参照

- 主流是**三段级联**（VAD → ASR → LLM → TTS），不是单个 omni 模型。
- 一体化服务：**Speaches**（自称「Ollama, but for TTS/STT」，faster-whisper + Piper/Kokoro，OpenAI 兼容 API，CPU/GPU 均支持）。
- 工程框架：Home Assistant 的 Wyoming 栈（faster-whisper + Piper）、LiveKit Agents、Pipecat。
- 真双工只有 omni 模型能做，且都要 GPU → 本轮不做（§8）。

## 4. 两套模式

### 4.1 方案 A：只转文本（默认档）

按住输入框说话 → 松手 → 转写 → 文本落进输入框（**不自动执行**），用户自己确认或改完再发。设置页可把「听」段换成精度更高的模型。

### 4.2 方案 B：完整回路「听 → 想 → 说」

转写 → 「想」段把模糊话补成完整需求 → **直接起 run** → （可选）「说」段用语音播报回复。设置页可逐段换模型；「想」段可选离线模型（选中才下载）。

### 4.3 防误伤（方案 B 的必要配套）

模糊语音直接执行 = 一句话识别错就跑一整轮。对策：

1. 转录里展示**实际发出的完整需求**（与既有的斜杠命令「提交前展开」同一口径：转录里看到的就是真发出去的）。
2. 起 run 前给**约 2 秒可撤销窗口**（Esc 或点「等等」即中止）。
3. 离线「想」段的等待时间必须如实显示（10–25 秒的进度，而不是静默卡住）。

## 5. 模型目录与按需下载

- 三段的候选都来自一张目录表，卡片字段：来源（在线 / 离线）、体积、运行位置（本机 CPU / 本机 GPU / 远端）、是否需下载、实测或预估性能。
- **未选择 = 不下载**。选中离线候选后才出现「下载」按钮（标体积）→ 下载中可取消 → 已就绪显示占用与「删除」。
- 下载实现沿用 `scripts/fetch-runtimes.mjs` 的下载 + 校验和做法（该脚本已负责 Node/Python/uv/JDK 的下载与校验），落到 `~/.kenfutwork/models/`。228MB 级文件**不入库**（《AGENTS.md》禁止提交产物）。
- 校验和不匹配即失败，且**不留半截文件**；失败给可读报错 + 手动放置路径 + 重试。
- 未下载的模型只显示**预估值并标注「预估」**（如 Qwen3-4B 的 10–20 tok/s），下载并检测后换成实测值。

## 6. 性能检测

- `POST /api/voice/diagnose`：
  - 硬件：CPU 型号与核数（`os.cpus()`）、内存（`os.totalmem()`）、GPU（`nvidia-smi` 尽力探测）。
  - 听：内置 4 秒中文样本 wav（16kHz 单声道，约 128KB，随测试资源）→ 实测转写耗时 → RTF。
  - 想：本地模型跑固定提示生成约 50 token 测 tok/s；在线/远端模型测**首 token 延迟**（语音闭环真正在意的是它）。
  - 说：合成固定短句，测首包耗时 → RTF。
- 判定收敛到纯函数 `apps/web/src/lib/voice-profile.ts`（与 `workbench-surface.ts` / `work-directory.ts` 同样的「纯逻辑 + 测试锁死」形状，便于单测钉死阈值）：
  - ASR：RTF ≤ 0.5 优 / ≤ 1.0 良 / > 2.0 差。
  - LLM：TTFT ≤ 1.5s 且 ≥ 15 tok/s → 推荐完整回路；8–15 tok/s 可用但有提示；< 8 tok/s 建议「想」用在线模型。
  - TTS：首包 ≤ 0.5s 且 RTF ≤ 1 → 推荐语音回复。
- 结果写 `app_config`（沿用权限档位那次「启动读回 + PUT 先写库再改内存」的单行写穿模式），提供「重新检测」。
- 检测约需半分钟：**可取消、不阻塞界面**；运行期每轮语音的实测耗时汇总成中位数显示在同一页（只记耗时，不记用户内容）。
- 检测**不删功能**：性能不足给红字警告 + 实测代价，用户可强制开；只有硬缺失（模型未下载、端点不可达）才置灰并写明原因——遵守仓库硬规则「不摆空壳、不放假开关」。

## 7. UI 与手势

- 设置 → 基础设置在「通用 / 外观 / 模型 / 供应商 / 浏览器」之后新增「语音」页：模式开关（只转文本 / 完整回路）、三段选择器（含在线/离线与下载状态）、检测报告与一键应用推荐、语音回复开关。
- 手势：`apps/web/src/lib/use-hold-to-talk.ts`
  - pointerdown 起 200ms 计时；期间移动 > 8px 或提前松手 = 普通点击/拖选（不录音，不干扰光标定位与选中）。
  - 满 200ms 进入录音态并 `setPointerCapture`；松手提交；Escape 或 pointercancel 丢弃。
  - 命中 `button` / `[role=button]` / `select` / `input` 不触发（按工具行按钮不会误录音）。
  - 录音态给一行状态（录音中 0:03 / 转写中… / 失败原因），期间临时 `user-select: none`。
- 录音链路：`getUserMedia` → `MediaRecorder`（webm/opus）→ `decodeAudioData` → 线性重采样到 16kHz 单声道 → **手写 WAV 编码（约 50 行）**。这样服务端与 provider 都不需要 ffmpeg，也不引入转码依赖。
- 三处接线（共用同一 hook 与状态条）：`workbench.tsx:2567-2745`（追问）、`workbench.tsx:2817-3045`（空态）、`chat-input.tsx:331-431`（Design 画布助手）。**删除两个麦克风占位按钮**（`workbench.tsx:2714-2720`、`3019-3025`）与随之无用的 import。
- 转写/改写结果写入必须走各组件既有的受控 state 与 `apps/web/src/lib/composer-edit.ts` 的写入路径——否则画布助手自管的 undo 历史会与 React state 脱钩。
- 顺手修路径上的既有缺陷：两处 workbench 输入框的 Enter 提交缺 `isComposing` 判定（中文输入法回车会提前提交；`chat-input.tsx:120-128` 有正确写法可参照）。
- 文案按《AGENTS.md》「界面文案只写给用户看」：一句说清（如「按住输入框说话，松开转文字」），不写实现细节。

## 8. 明确不做

- 真·双工与回声消除、亚秒往返（CPU 上不现实，需要 GPU 或云端）。
- 唤醒词与常驻监听（VAD 只做离线切句，不做全天候监听）。
- 多说话人、音色克隆。
- 把模型打进安装包（与桌面端常驻内存预算冲突）。
- 通话记录留存（只留耗时统计，不留音频与文本）。

## 10. 风险与未决

1. **Qwen3-4B 的 CPU 吞吐是推算值**（第三方实测未取到可信来源）→ 由上机检测量准并写回 §3.2；在此之前界面一律标「预估」。
2. **原生 addon 的打包**：`sherpa-onnx-node` 的平台包（如 `sherpa-onnx-win-x64`）需进 `optionalDependencies`（与现有平台二进制同做法），且要单独验证 Node SEA 打包下 `.node` 能否正确加载。
3. **检测耗时**约半分钟 → 必须可取消 + 结果缓存，首次进入不阻塞界面。
4. **自动执行的误伤**（方案 B）→ 完整需求可见 + 2 秒撤销窗口兜底，且必须真实模拟点击验收（单测覆盖不到这类回归）。
5. **下载失败/中断** → 校验和不匹配即失败、不留半截文件，可读报错 + 手动放置路径 + 重试。
6. **样本 wav 的代表性**决定检测结论 → 样本与阈值都进测试，改阈值必须过单测。
7. **许可**：SenseVoice 代码 MIT、**权重走 FunASR 模型许可（需署名）**；Kokoro 与 sherpa-onnx 为 Apache-2.0（与本项目 GPL-3.0 兼容）。署名位置：设置 → 关于。
