# 米家插件规划

> 角色：**调研 + 方案规划**（参考级，非权威）。结论拍板后落地写入《改造计划》§4.13 台账。
> 状态：待拍板（2026-09-18 首次成稿）。
> 需求来源：2026-09-18 用户提出的四条硬要求（见 §1.1）。所有「实测」结论均在本机代码上核对过，附文件与行号。

## 0. 结论速览

| 路线 | 一句话 | 改动量 | 可装/可卸 | agent 可控 | 重启后不失效不扫码 |
| --- | --- | --- | --- | --- | --- |
| **A 现成 App（Home Assistant）+ 最小接入** | 让 HA 顶替手机米家 App，本项目只对接 HA | 零代码（A1）/ 约 30 行（A2）/ 约 300 行（A3） | A2、A3 可（插件形态） | 是 | 是 |
| B 自研米家云客户端 + 给内核补存储能力 | 自包含、不依赖外部服务 | 最大：插件能力 1 项 + 迁移 1 张 + 插件本体约 800 行 | 是 | 是 | 是 |
| C 纯 MCP | 只让 agent 控制，不做设备面板 | 零代码 | 不适用 | 是 | 是 |

**推荐路线 A**。理由：小米账号登录与设备协议留在 HA 里，本项目只持有一个有效期 10 年的 HA 长期令牌；既不碰社区逆向的云接口，也不碰官方集成「禁止用于其他软件」的许可证。A1 直接复用项目已有的 MCP 通道（server 配置落库，天然跨重启）。**若不愿运行第三方 App，才走 B**（自包含，但最脆：逆向接口 + 扫码风控）。

## 1. 需求与项目侧硬约束

### 1.1 需求（四条，缺一不可）

1. 米家能力以**插件**形态交付：需要安装、可以卸载（走既有插件市场机制）。
2. **侧边栏**能看到并控制米家设备。
3. 安装后 **agent 能控制设备**（不要求用户先打开面板）。
4. 服务端**重启后凭证不失效**，不需要重新扫码。

需求 3 与 4 共同决定了：凭证必须服务端可持久化。而这一点恰好是当前插件系统的空白（§1.3）。

### 1.2 插件能力面（实测）

- 第三方 bundle 受控的能力面只有四项：`tools`、`systemPrompt`、`routes`、`ui`；其余十项（`settings`/`jobs`/`llm`/`sessions`/`commands`/`fs`/`subprocess`/`sandbox`/`agents`）在绑定表里**显式拒绝并给出理由**（`apps/server/src/features/plugins/capability-binding.ts:32-111`）。
- 插件以 `{ name, inject, apply(ctx) }` 形状在**服务端进程内**被动态 `import()` 装载（`apps/server/src/features/plugins/plugin-registry-service.ts`，装载点在 `features/plugins/plugin.ts`）。
- `ctx.routes.register` 的 handler 能拿到 `method/path/query/body/headers`（`plugin-registry-service.ts:661-676`，派发入口 `apps/server/src/http/plugins.ts:261-301`）；**公共路由**（`public: true`）不需要登录，私有路由要求 `Authorization`。

### 1.3 三条硬边界（决定了 B 路线的存在理由）

1. **没有存储能力**：`ctx` 面里没有 DB、没有密钥、没有设置、没有环境变量通道；唯一副作用手段是 `ctx.effect`（自管定时器）。插件重启即失忆。
2. **门禁禁止直连系统**：`node:fs`、`child_process`、`vm`、`cluster`、`worker_threads` 的字面 import 一律判 blocker（`apps/server/src/features/plugins/module-scan.ts:33-44`）——这是兼容性判据而非安全沙箱，但结论是插件**不能**自己落盘。
3. **bundle 不能带 npm 依赖**：GitHub 来源跳过 `node_modules` 且只收文本白名单（`.json/.js/.yml/.md/.html/.css/.svg`，单文件 512KB；`apps/server/src/features/plugins/bundle-source.ts:49-80`），安装期也不跑包管理器。因此插件若要说话，必须自带无依赖实现。

### 1.4 UI 与凭证的既有形态（实测）

- 插件 UI 只有四个固定槽位：`sidebar` / `conversation` / `canvas` / `settings`；`sidebar` 在工作台左栏渲染成**一行入口**，点开是 80vh 的 iframe 弹层（`apps/web/src/components/workbench/workbench.tsx:2027-2042`、`apps/web/src/lib/plugin-panels.tsx:97-131`）。
- 面板 URL 支持**外链** `http(s)://…`，也支持相对插件路径（`plugin-panels.tsx:87-94`）。
- 面板 iframe **带不上 `Authorization` 头**（`apps/server/src/http/plugins.ts:254-260` 的注释写明），所以插件面板要么走 `public` 路由（不安全：任何能访问服务端的人都能读），要么另想办法拿登录态。
- 安装 / 卸载 / 停用都要**管理员**（`http/plugins.ts:123-147、189-252、330-375`）；卸载 = 收回贡献物 + 调 dispose + 删 bundle 目录 + 清 `installed.json` 记录（`plugin-registry-service.ts:440-450、704-719`）。插件落盘目录默认 `<cwd>/.kenfutwork/plugins`（`features/plugins/plugin.ts:47-52`，已被 gitignore）。

### 1.5 项目侧可复用的既有设施

- **MCP 通道**：MCP server 以 stdio 子进程连接（`apps/server/src/features/mcp/mcp-service.ts:2`），`command/args/env` 存 `mcp_servers` 表（`features/mcp/server-store.ts`，env 写库、HTTP 只回键名），运行时增删/重连有管理界面。
- **危险工具表**：`mcp__*` 前缀命中 `/^mcp__/`（`apps/server/src/features/permissions/permission-service.ts:31-42`）→ 默认档下 MCP 工具调用需要审批。
- **存储缝范式**（仅 B 路线需要）：`persistence.forWorkspace(id)` + SQL 必须显式带 `:workspace` 谓词，漏写立即失败（`apps/server/src/features/persistence/types.ts:17-25`）；凭证加密复用 `features/model-providers/secret-store.ts`（scrypt 派生 AES-256-GCM，密钥来自 `KENFUTWORK_CREDENTIAL_SECRET`）；迁移模板见 `supabase/migrations/20260917230000_api_tokens.sql`。
- 工具执行上下文里有 `workspaceId`（`apps/server/src/kernel/types.ts:203`），但插件路由的 handler 目前**拿不到工作区/用户身份**（只知是否登录）。

## 2. 现成方案调研：能不能顶替手机米家 App

### 2.1 先排除的三类

- **官方米家网页版**：不存在。`home.mi.com` 现在是米家商城（页面 title「米家」，描述「米家商城 一键购买…」），不是设备控制台；未检索到官方 PC 客户端。
- **可复用的开源手机客户端**：没有。F-Droid 无米家客户端；第三方只有 `MiHome-Client`（HarmonyOS，11★，不能添加设备、无对外 API）与 `MiHome-Windows`（Windows 桌面端，65★，无 API）；都不可复用。
- **「米家修改版 APK」**：闭源重打包，违反用户协议、可能封号，且持有完整小米账号凭据（含设备 token）。不推荐、不作为集成底座。

### 2.3 小米侧的事实（决定「自研」路线的成本）

- **账密登录基本不可用**：登录普遍触发验证码 / 2FA；社区通行做法是**扫码**（`Do1e/mijia-api` 的 FAQ 直言「现在登录似乎 100% 遇到验证码，建议使用扫码登录」）。
- **设备 token 提取已退化**：米家 App > 5.0.19 不再写 `miio2.db`，本地提取基本失效；云提取工具在 2025-09 才补上扫码与 2FA（且 2FA 有 3~5 次/天 的频率限制）。
- **本地直控门槛高**：需要设备 token + 同网段（Docker 还要 host 网络），且只覆盖 WiFi/网线设备，ZigBee / BLE Mesh 子设备要靠网关或云。
- **MIoT-Spec-V2 是公开数据源**：`miot-spec.org` 的 `/miot-spec-v2/instance?type=…` 匿名可用，自研时用来生成控件。
- 参考实现（许可证干净、可读不可抄进产品）：`merdok/homebridge-miot`（MIT，`lib/protocol/MiCloud.js` 含扫码登录三步与签名算法）、`@mi-gpt/miot`（MIT，TS）。已停更勿用：`node-mihome`（2022 起无维护、无 MIoT-Spec）。

## 3. 三条落地路线

### 路线 A：现成 App（Home Assistant）+ 最小接入 —— **推荐**

把 HA 当「米家 App 的替代品」（它自带 Web UI 与官方手机 App），本项目只做三件事，按需叠加：

- **A1 agent 可控（零代码）**：在既有 MCP 面板新增一条 server，用 `mcp-remote` 把 HA 的流式 HTTP MCP 桥成 stdio：
  `npx -y mcp-remote <HA地址>/api/mcp --header "Authorization: Bearer <HA长期令牌>"`
  MCP 的 `env`/`args` 落库，**服务端重启后依然可用**；HA 侧的小米登录态由 HA 持久化，不需要再扫码。工具以 `mcp__<name>__<tool>` 进入统一注册表。
- **A2 侧栏入口（约 30 行插件，零核心改动）**：新建插件 bundle，清单只声明 `kenfutwork.ui`，`slot: sidebar`、`url` 指向 HA 仪表盘地址（面板支持外链）。装/卸载即增删侧栏那一行。前置：HA 关掉 "Send X-Frame-Options" 才能被 iframe 嵌入；关不掉就退化成「在新标签打开 HA」按钮。
- **A3 自建薄面板（可选，约 300 行）**：插件自带面板页，直连 HA REST（`GET /api/states`、`POST /api/services/<domain>/<service>`）。注意必须**浏览器直连**（HA 侧开 `cors_allowed_origins`，HA 令牌存面板 localStorage）；若改成经插件路由代理，令牌就要服务端持有，从而落回路线 B 的存储问题。

HA 侧事实：MCP 自 HA 2025.2 起内置于 `mcp_server` 集成，端点为 `POST /api/mcp`（streamable HTTP、无状态），鉴权可用长期访问令牌；暴露范围限于「暴露给 Assist 的实体」，可通过配置项调整。REST 与 WebSocket 均用同一个长期令牌鉴权，该令牌有效期 10 年。

### 路线 B：自研米家云客户端 + 给内核补存储能力

自包含、不依赖任何外部服务，但要动内核：

1. 新增插件能力 `storage`（`ctx.storage.get/set/delete/keys`）：按 `(工作区, 插件, key)` 存，值经 `secret-store` 加密落库，HTTP 永不回显；卸载 purge、停用保留。落点：`packages/shared` 的能力名清单 + `capability-binding.ts` 一行 + `compat-context.ts` 成员 + 存储 Provider + 1 张迁移（范式同 `api_tokens`）。绑定表注释与治理规则要求能力面唯一属主，故新能力必须在绑定表登记。
2. 插件写无依赖的米家云客户端：扫码登录三步（`longPolling/loginUrl` → 轮询 `lp` → `location` 换 token/cookie）、请求签名（nonce / signedNonce / HMAC-SHA256，必要时补 RC4）、`home/device_list`、`miotspec/prop/get|set`、`miotspec/action`；控件模型由 MIoT-Spec 驱动（开关 / 亮度 / 读数），离线设备置灰、无控件品类如实标「仅状态」。
3. 面板与工具：面板仍是侧栏入口弹层；由于 iframe 带不上 `Authorization`，需要额外补一处**登录态握手**（工作台把 access_token 用 `postMessage` 递给同源面板），否则面板只能走 `public` 路由（不安全）。

风险：云接口是社区逆向（有风控与变更风险）、扫码是唯一稳定登录路径、serviceToken 需静默续期、失败模式对用户不友好。

### 路线 C：纯 MCP

零代码，只有 agent 工具、没有设备面板 UI。可用现成包直接接：

- `npx -y @zythum02/mijia-api mcp`（npm，TS，扫码登录，token 30 天自动续，缓存 `~/.config/mijia-api`；GPL-3.0-or-later）。
- `uvx mijiaAPI mcp`（`Do1e/mijia-api`，Python，功能最全；GPL-3.0；需本机 Python）。
- HA 的 MCP（同 A1）——本质也是 C，但小米协议交给 HA 维护，登录用 HA 令牌而非小米扫码。

## 4. 推荐路径与步骤（路线 A）

**前置（用户侧，一次性）**：Docker 起 HA（官方镜像即可，不要求 HAOS）→ 装 Xiaomi Home 集成（HACS 或手动拷 `custom_components/xiaomi_home`）→ 小米账号 OAuth 扫码一次并选对区域 → 在「个人资料 → 安全」创建长期访问令牌 → 把要控的实体暴露给 Assist。
> 验证：浏览器打开 HA 仪表盘能开关灯/插座、看到传感器读数（此时 HA 已经是「你的米家 App」）。

**仓库侧**：

1. A1：MCP 面板新增 `npx -y mcp-remote …` 一条。
   - 验证：工具列表出现 `mcp__*`；对 agent 说「把客厅灯打开」，HA 中状态跟随变化。
   - 验证（关键）：**重启服务端，不重新授权**，再下一条控制指令仍生效。
2. A2：插件 bundle（清单声明侧栏槽位 + 外链 HA 面板）。
   - 验证：市场安装后侧栏出现入口、点开可控制；停用后入口消失、工具消失；卸载后目录与 `installed.json` 记录清空。
3. A3（可选）：自建薄面板。
   - 验证：`pnpm lint`、`pnpm typecheck`、`pnpm test` + 模拟点击走查（扫码/登录一次 → 设备网格 → 开关真实生效）。
4. 台账：落地时在《改造计划》§4.13 记账（同一提交）。

## 5. 已知限制与风险

1. **审批门**：`mcp__*` 命中危险工具表，默认档下每次控制都要审批；可在设置 → 权限 → 自定义加允许规则，或切「自动审批/完全访问」档。
2. **`npx` 依赖**：桌面 exe 随包运行时 `npx` 可能不在 PATH，需要本机具备 Node；后续可把 `mcp-remote` 收进随包运行时。
3. **HA 令牌落库口径**：MCP 的 env 与 `mcp_servers` 表同库同权限（非 BYOK 那套工作区隔离 + 加密），属实例级配置；自托管多用户场景需注意。
4. **嵌入 HA 前端**：默认 `X-Frame-Options: SAMEORIGIN`，需在 HA 里关闭才能在面板内显示；iframe 内还要再登录一次 HA；关不掉则退化为「新标签打开」。
5. **外部依赖**：HA 及其小米集成的版本、区域、掉线由用户维护；官方集成 2026 年维护放缓，社区集成可替代（对我们只是「HA 实体/服务」）。
6. **路线 B 的额外风险**：社区逆向的云接口可能变更、扫码存在风控、需要新的内核能力（属于架构级改动，须走 §4.13 台账与门禁）。
7. **多工作区口径**：A1 的 MCP 是实例级——同一实例的所有工作区共用同一个 HA（也就共用同一份米家账号）。B 路线按工作区隔离，但需要额外把工作区身份传进插件路由。

## 6. 待拍板问题

1. 是否已有 / 愿意常驻一台 Home Assistant？（决定 A 还是 B）
2. 侧栏面板形态：嵌 HA 前端（A2，最省）还是自建薄面板（A3，观感统一但要维护 UI）？
3. 是否接受「每次设备控制需审批」的默认档（或改设置档位 / 自定义允许规则）？
4. 是否要在桌面随包预置 `mcp-remote`（免去用户本机装 Node）？
5. 若走 B：新增插件 `storage` 能力是否立项（内核改动，需要单独提案与迁移）。
