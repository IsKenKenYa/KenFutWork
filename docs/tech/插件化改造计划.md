# 插件化改造计划（参考 deepseek-harness × nomifun）

> 状态：**计划稿 v2（未实施）**。v1 确立了「一切皆插件」的内核与分阶段路线；v2 纳入产品方向修订——**向 BYOK（用户自带 Key）自定义供应商/模型的 Work 画布创作平台转型**，参考 Cherry Studio 与 `references/nomifun-tauri` 的供应商架构。Supabase 不移除，但从「贯穿全码库的硬依赖」降级为可插拔的适配器之一。多端形态（Tauri 桌面 / Docker 自部署 / Web / 移动）见下游文档 `docs/tech/多端产品架构计划.md`。改造尚未开始；落地时按阶段逐 PR 推进，每个 PR 行为不变、测试护航。

## 1. 产品方向：BYOK Work 画布平台

### 1.1 对标产品的共同模式

Cherry Studio 与 nomifun（`references/nomifun-tauri`）的自定义供应商架构是同一个模式，nomifun 的实现最值得抄：

- **线协议适配器是小而封闭的集合**（`crates/agent/nomi-providers/`）：`anthropic` / `openai` / `openai_responses` / `gemini` / `bedrock` / `vertex` 六种 wire protocol。**"自定义供应商"不是每种供应商写一个适配器，而是协议适配器之上的用户命名实例**——绝大多数"新供应商"（DeepSeek、月之暗面、OpenRouter、Ollama、各类中转网关）都是 OpenAI 兼容协议的另一个 `base_url`。
- **ProviderConfig = 用户命名实例**（`nomi-config/src/config.rs`）：`{ provider: 底层协议类型, model, api_key, base_url, prompt_caching, compat }`。`compat`（`ProviderCompat`）是兼容性开关集，吸收各家中转网关的协议小毛病（如 `max_tokens` 字段改名、tool result 双重编码）。
- **Profile = 供应商 + 模型 + 参数的一等打包**：`{ provider, model, max_tokens, extends, mcp_servers }`，用户可命名、可继承、可切换。

### 1.2 Loomic 现状与目标的差距

| 维度 | 现状（SaaS 形态，env 驱动） | 目标（BYOK Work 形态） |
| --- | --- | --- |
| 模型目录 | `apps/server/src/http/models.ts` 硬编码静态数组（`openai:*` / `google:*` 前缀） | 从用户供应商实例动态推导目录 |
| 供应商凭证 | 服务端 env：`openAIApiKey` / `googleApiKey` / `replicateApiToken` / `volcesApiKey` / `metasoApiKey` | 用户自带 Key，按工作区存储、按需实例化 |
| agent 模型选择 | `agent/deep-agent.ts` 按 env 三选一（ChatOpenAI / ChatGoogleGenerativeAI / ChatVertexAI） | 按用户选定的供应商实例 + 模型实例化对应协议适配器 |
| 图/视频生成 | `generation/providers/` 按 env 注册 replicate / google / volces / metaso | 协议适配器固定，实例来自用户配置；平台托管池为可选兜底 |
| 存储/认证 | Supabase 直连散布在各 feature service（`createUserClient` / `getAdminClient` + `.from()`） | Supabase 收拢为存储适配器；凭证存取走窄缝接口 |
| 计费 | credits + Lemon Squeezy 全量计费 | **待产品决策**（见 §6）：保守方案 = 用户自有 Key 的调用免费，平台托管模型才计费 |

### 1.3 形态澄清

nomifun 是 Tauri 桌面应用（local-first）。Loomic 保持 **web 平台形态**（Next.js + Fastify，server 已有 Dockerfile 可自部署），转型的是**供应商/模型主权**（用户配置、用户 Key、用户数据），不是部署形态。

## 2. deepseek-harness 理念提炼

deepseek-harness（`dsh`）建立在 Cordis 之上，核心主张：**没有特权核心，产品的每个部分都是插件**——模型适配器、工具注册表、会话日志、甚至 agent 主循环本身。可借鉴的理念有以下八条：

1. **插件是唯一扩展方式**：扩展 = 在其他插件旁边挂载新插件，而不是修改核心。
2. **Context 是服务仓库**：服务认领稳定的 `ctx.<key>`，其他插件按 key 发现服务，而不是 import 具体实现。
3. **`inject` 声明依赖**：加载顺序由「服务需求」拓扑表达，不靠手工 boot 时序。
4. **事件即扩展点**：拦截和策略挂类型化事件（emit / waterfall / parallel / serial / bail）；waterfall 监听器必须调 `next()` 委托。
5. **注册即可逆副作用**：一切贡献通过 `ctx.effect()` 安装并返回 disposer，插件卸载逆序回卷。
6. **Profile 与 Bundle**：一次运行 = 启动时按有序层组合的插件树；`--dump-config` 可观测。
7. **能力缝三元组**：可替换能力 = Service Definition + Service Provider + Consumer，三者齐备才叫缝。
8. **配置目录化 + fail loud**：无硬编码 tunables；misconfiguration 在加载期报错，绝不静默跳过。

### 裁剪决策：不引入 Cordis 本体

| 考量 | 结论 |
| --- | --- |
| Cordis 处于 developer preview，README 明示「THERE WILL BE COMPATIBILITY-BREAKING CHANGES」 | 不引入 |
| dsh 的 profile/patch/热重载服务于「可组合发行版」；本项目是固定两进程应用 | 不引入 YAML 组合层 |
| 本项目行为准则：简洁优先、禁止大爆炸重写、不为投机性灵活性堆抽象 | 自建 ~150 行内核，只取「依赖注入 + 拓扑挂载 + 显式覆盖」 |
| 事件总线当前没有第二个真实消费者 | 事件机制暂缓（见 §8 非目标） |

## 3. 当前项目诊断

### 3.1 已有的萌芽态插件缝（改造的地基）

| 缝 | 位置 | 现状 |
| --- | --- | --- |
| 生成 provider 注册表 | `apps/server/src/generation/providers/registry.ts` + `register-all.ts` | Map 注册表 + 副作用批量注册；server 和 worker 各自调用，靠人肉保持一致 |
| 任务 executor 注册表 | `apps/server/src/features/jobs/job-executor.ts` | `registerExecutor()`；executor 通过 worker.ts 顶部副作用 import 隐式激活 |
| Agent 后端工厂 | `apps/server/src/agent/backends/index.ts` | 按 `agentBackendMode` 在 dev（filesystem）/ prod（state）间选择 |
| HTTP 路由 | `apps/server/src/http/<feature>.ts` | 每特性独立 `registerXxxRoutes(app, deps)`，已是插件形状的半成品 |
| 认证 | `apps/server/src/supabase/user.ts` 的 `RequestAuthenticator` | 已是接口；但唯一实现绑定 Supabase JWT |

### 3.2 痛点

**装配层**：`apps/server/src/app.ts` 424 行特权核心——30+ import、12 个服务手工构造、21 个路由调用、条件注册内嵌（paymentService / jobService）、`BuildAppOptions` 17 个测试覆盖项。新增 feature 改四处。

**供应商主权**：模型目录硬编码在 `http/models.ts`；agent 模型三选一硬编码在 `deep-agent.ts`；图/视频 provider 按**服务端** env 注册。用户无法添加自己的供应商/模型/Key——这是与目标产品的本质差距。

**存储耦合**：各 feature service 直接持有 Supabase client 并 `.from()` 查询；供应商凭证若存 workspace 级配置，会继续加深这种耦合。

## 4. 目标架构

### 4.1 内核（`apps/server/src/kernel/`，约 150 行）

```ts
// types.ts
export type ServiceKey = "viewer" | "projects" | /* 全部 ctx key，见 §4.2 */;

export interface PluginDefinition {
  name: string;                            // 稳定 id，用于挂载日志与诊断
  inject: ServiceKey[];                    // 依赖的服务 key，compose 据此拓扑排序
  enabled?: (env: ServerEnv) => boolean;   // 缺省 true；payment/jobs 类开关收编于此
  apply(ctx: PluginContext): void | (() => void);  // 返回 disposer
}

// context.ts
export interface PluginContext {
  register<K extends ServiceKey>(key: K, factory: (deps: DepsOf<K>) => ServiceOf<K>): void;
  get<K extends ServiceKey>(key: K): ServiceOf<K>;   // 未注册即抛错（fail loud）
  effect(fn: () => void | (() => void)): void;
  app: FastifyInstance;
  env: ServerEnv;
}

// compose.ts
export function composePlugins(plugins: PluginDefinition[], overrides?: Partial<ServiceMap>): () => void;
```

职责边界：**服务单例语义归 kernel ctx，HTTP 封装语义归 Fastify `app.register()`**。

### 4.2 ctx key 表（稳定契约，新增须改此处）

| ctx key | 服务 | 备注 |
| --- | --- | --- |
| `viewer` | ViewerService | 用户/工作区引导 |
| `projects` / `brandKit` / `canvas` / `threads` / `chat` / `settings` / `uploads` | 各领域服务 | 同 v1 |
| `agentRunMetadata` / `agentPersistence` / `agentRuns` | agent 运行时三件套 | 同 v1 |
| `jobs` | JobService（PGMQ） | `enabled: 有 supabaseDbUrl` |
| `credits` / `tierGuard` / `payments` | 计费三件套 | BYOK 下仅对平台托管模型生效（§6） |
| `generation` | 图/视频协议适配器注册表 | 实例化时接受 ProviderInstanceConfig |
| `modelProviders` | **用户供应商实例管理（CRUD + 解析）** | 新增，见 §4.3 |
| `modelCatalog` | 模型目录（用户实例推导 + 平台托管合并） | 新增，取代硬编码 `http/models.ts` 数组 |
| `auth` | RequestAuthenticator | 已有接口；Supabase JWT 为一种实现 |
| `backend` | agent 后端工厂 | 同 v1 |
| `ws` | ConnectionManager + EventBuffer | 同 v1 |

依赖拓扑（`inject` 依据，环即 fail loud）：`viewer` → `projects/canvas/brandKit/threads/settings/uploads/modelProviders` → `chat`（依赖 threads）、`modelCatalog`（依赖 modelProviders）→ `jobs/credits/tierGuard/payments` → `agentRuns`（依赖最多，最后挂载）。

### 4.3 一等能力缝（BYOK 转型的核心）

**模型供应商缝（model provider seam）**——完全按 dsh 三元组设计：

- **Service Definition**（`packages/shared` 新增 zod 契约 + server 接口）：
  ```ts
  // 供应商实例 = 协议类型 + 连接信息 + 模型清单 + 兼容开关（nomifun ProviderConfig 模式）
  ProviderInstanceConfig = {
    id, workspaceId, name,
    protocol: "openai-compatible" | "anthropic" | "gemini"   // 封闭集合，v1 三种
    | "google-image" | "replicate" | "volces" | "metaso",    // 图/视频协议
    baseUrl?, apiKeyRef,            // apiKeyRef 指向凭证存储，不落日志/不回传前端
    models: [{ id, name, capability: "chat"|"image"|"video" }],
    compat?: { ... },               // 兼容开关集，按协议定义
    enabled: boolean,
  }
  ```
- **Service Provider**：`apps/server/src/providers/` 下的线协议适配器——聊天侧复用 LangChain 的 `ChatOpenAI`（OpenAI 兼容） / `ChatAnthropic` / `ChatGoogleGenerativeAI`（nomifun 同款封闭集合思路，LangChain 已提供实现，不手写 HTTP）；图/视频侧复用现有 `generation/providers/` 六个实现，把「从 env 读凭证」改为「从 ProviderInstanceConfig 读」。每个适配器声明其 `compat` 开关集。
- **Consumer**：`deep-agent.ts` 按运行时传入的实例实例化聊天模型；generation pipeline 按任务携带的实例实例化图/视频适配器；`modelCatalog` 路由向前端返回可用目录。

**存储窄缝（storage seam）**——克制起步，不做全量查询抽象：

- `ctx.auth`：`RequestAuthenticator` 接口化收拢（已有接口，唯一实现是 Supabase JWT；local/self-host 模式将来加静态 token 实现）。
- 凭证存取：`apiKeyRef → apiKey` 的解析走 `modelProviders` 服务内部封装（v1 存 `workspace_settings` 同级的 Supabase 表，RLS 按工作区隔离；服务端解密/读取后仅内存持有）。
- **关系数据查询不做全量抽象，但保持内聚**：feature service 的数据访问收拢在各 feature 目录内，为后续 repository 接口抽取留好接缝——桌面本地优先形态（Tauri sidecar + PGlite/SQLite 驱动）出现后，`ctx.storage` 缝升级为一等缝，承接计划见 `docs/tech/多端产品架构计划.md` §5（D1 阶段）。

### 4.4 插件目录约定

```text
apps/server/src/features/<feature>/
  plugin.ts              # PluginDefinition：inject + enabled + apply
  <feature>-service.ts
  *.test.ts
apps/server/src/providers/<protocol>/
  <protocol>-adapter.ts  # 线协议适配器（Service Provider）
```

### 4.5 Profile：两个进程共享一棵插件树

```ts
// profiles/server.ts —— HTTP + WS + agent（含 modelProviders/modelCatalog 插件）
// profiles/worker.ts —— 队列 + executor（复用 generation 插件；job 执行时按任务携带的实例动态实例化适配器）
// profiles/test.ts   —— server 同款 + overrides 注入 mock
```

`server.ts` / `worker.ts` 退化为「选 profile → composePlugins() → listen」。开发环境 compose 后打印挂载树（`dsh --dump-config` 的轻量等价物）。

### 4.6 扩展点速查表

| 目标 | 机制 | 不再改 |
| --- | --- | --- |
| 接入新供应商（OpenAI 兼容网关等） | 前端「供应商设置」添加实例——**零代码** | 任何服务端文件 |
| 新线协议（如新的原生 SDK 协议） | `providers/<protocol>/` 新适配器 + `ProviderInstanceConfig.protocol` 联合类型扩一项 | 适配器之外的代码 |
| 新增图/视频 provider 能力 | `generation/providers/` 实现接口，经 `generation` 缝注册 | server/worker 两处注册路径 |
| 新增 agent 工具 | 所属 feature 插件 `apply()` 内注册 | `tools/index.ts` |
| 新增 HTTP 路由 | feature 插件 `apply()` 内 `ctx.app.register()` | `app.ts` |
| 新增后台任务 | executor 调 `registerExecutor()` | `worker.ts` import 清单 |
| 新增业务 feature | 新建 `features/<x>/plugin.ts` + profile 清单加一行 | `app.ts` 全部四处 |

## 5. 共享契约变更（packages/shared）

- 新增 `provider-contracts.ts`：`ProviderInstanceConfig` / `ProviderCompat` / 模型能力联合 / 目录响应 schema（服务端 zod 单一事实源，前后端共享）。
- `contracts.ts` 的 `ModelInfo` 扩展 `providerInstanceId` 字段（区分平台托管与用户实例）。
- ws/job 契约：生成任务 payload 携带 `providerInstanceId` + 模型 id，worker 据此实例化适配器。
- 契约先行：本节 schema 定稿并合入 `packages/shared` 后，服务端改造才开工（编译器牵引两端）。

## 6. 待产品决策（实现前必须定）

1. **计费口径**：保守方案 = 用户自有 Key 调用免费、平台托管模型（平台 Key 池）按 credits 计费；激进方案 = 完全去 credits。影响 `credits/tierGuard/payments` 插件的 enabled 逻辑与水印策略。
2. **凭证安全边界**：v1 方案 = API Key 服务端加密落库（Supabase 表 + RLS）、仅服务端解密、永不回传前端（前端只写不读）。若要求端到端"Key 不落服务端明文"，需引入按工作区密钥封装，复杂度显著上升。
3. **agent 聊天模型与图/视频模型是否共用同一供应商实例表**：建议共用（一张表 + capability 标注），但 agent 侧 compat 开关集与生成侧不同。

## 8. 风险与对策 / 非目标

| 风险 | 对策 |
| --- | --- |
| `agentRuns` 依赖 8+ 服务，拓扑深 | compose 检测环即抛错；允许迁移中合并粗粒度 key，但须同步 §4.2 |
| Fastify 封装作用域与 kernel 单例冲突 | 硬边界：服务走 ctx（全局单例），Fastify 只承担路由封装 |
| 凭证泄漏面扩大（BYOK 引入用户 Key） | Key 只写不读、日志脱敏（参考 nomifun `SecretRedactor`）、RLS 工作区隔离、不落 worker 日志 |
| LangChain 适配器不覆盖某 compat 场景 | `ProviderCompat` 开关集兜底（nomifun 同款思路）；确需绕过时走 openai-compatible 的原始 fetch 通道 |
| server/worker 注册清单漂移 | Phase 6 后共享 profile 定义，漂移在编译期消失 |
| 测试搬迁量大 | `overrides: Partial<ServiceMap>` 机械映射；每 PR 只动一个 feature |

**非目标（明确不做）**：
- 不引入 Cordis / 任何第三方插件框架（含 YAML 组合、patch、live reload）；
- 不建通用事件总线——信用扣减、水印等拦截点保持直接调用，出现第二个真实消费者再按 waterfall 语义设计；
- **不在本计划内做存储后端抽象 / repository 化**——Supabase 保留为默认实现，数据访问保持 feature 内聚即可；`ctx.storage` 缝由多端计划的 D1 阶段（桌面本地驱动）正式承接；
- 前端不做对称插件化——Next.js App Router 文件路由本身就是插件系统；
- 不做桌面/local-first 形态转型（保持 web 平台 + 可自部署 Docker）；
- 不改既有 `packages/shared` 契约的语义（只做 §5 的增量扩展）。

## 9. 完成度量

- `app.ts` < 100 行且不 import 任何 `features/*`；
- 用户在前端「供应商设置」添加一个 OpenAI 兼容供应商并完成一次对话 + 一次图生成，**服务端零代码变更**；
- `http/models.ts` 硬编码目录、`deep-agent.ts` 的 env 三选一、`register-all.ts` 副作用注册全部退役；
- server 与 worker 的注册来自同一棵插件树，无人工同步点；
- `BuildAppOptions` 消失，测试覆盖统一为 `overrides: Partial<ServiceMap>`。
