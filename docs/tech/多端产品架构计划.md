# 多端产品架构计划（桌面 / 自部署 / Web / 移动）

> 状态：**概念阶段计划（未实施，不含代码）**。产品形态目标：**BYOK Work 画布平台**，以 Tauri 桌面端为主形态，服务端同码三种部署（桌面内嵌 / Docker 自部署 / 云端），Web 与移动端为客户端形态；沙箱与本机操控对标 nomifun；继续开源（GPL-3.0）。上游文档：`docs/tech/插件化改造计划.md`（服务端插件内核与 BYOK 供应商缝，本文的架构地基）。

## 1. 产品形态矩阵

| 形态 | 技术 | 角色 | 数据位置 | 优先级 |
| --- | --- | --- | --- | --- |
| **桌面端（主形态）** | Tauri 2（macOS / Windows / Linux） | Web UI + 内嵌服务端（sidecar）+ 本地 Worker + 沙箱宿主 | 本机 | P0 |
| **自部署服务端** | 同一服务端代码，Docker 镜像 | 无头 server + worker，多用户工作区，BYOK | 自选数据库 | P1 |
| **Web 客户端** | Next.js 静态导出（现有 `apps/web`） | 浏览器连任意服务端（桌面 loopback 或远程自部署） | 跟随服务端 | P1 |
| **移动客户端** | Tauri 2 Mobile（iOS / Android） | 薄客户端，QR 配对连接服务端；可选轻量 Worker | 跟随服务端 | P2 |
| **移动 Worker** | 同上，受平台限制的能力节点 | 分享流入、相机、语音、通知；无 shell、无任意文件访问 | 端侧受限 | P3 |

**统一原则：一份服务端代码，三种部署；一份 Web UI，三种外壳（Tauri 桌面窗口 / 浏览器 / Tauri 移动 WebView）。** 桌面端不是独立产品，而是「服务端 + 客户端」在本机的整体封装——数据天然本地优先（服务端跑在本机，数据落本机存储），Web/移动端连接任意一个服务端实例。

## 2. 参考架构提炼

### 2.1 nomifun 桌面模式（`references/nomifun-tauri`）

- **Tauri 2 + 内嵌 server**：`apps/desktop`（Rust）把 React UI 产物（`ui/dist`）作为资源打包，Rust 后端以「embedded-server」形式随应用进程运行（`nomifun-app` crate 是组合根）；非 Electron，用系统 WebView。
- **能力 crate 化**：computer-use（`nomi-computer`：screen/input/permissions/launch）、PTY 终端（`nomifun-terminal`）、文件（`nomifun-file`）、shell、SSH、浏览器平台各为独立 crate，由组合根按配置装配。
- **移动端独立仓库**（`nomifun-mobile`，Android/iOS/H5）：**不重写能力，只复用桌面会话**——桌面端开启「WebUI 访问」后，移动端扫一次性 QR 配对（`relay_pairing.rs`），直接复用会话、任务与能力。
- **本地存储**：SQLite + 内嵌迁移 + repository traits（`nomifun-db`）。

### 2.2 deepseek-harness 沙箱模型（`references/deepseek-harness/packages/sandbox`）

- **三档囚禁模式**：`read-only`（只读执行）/ `workspace-write`（仅会话工作区内可写）/ `danger-full-access`（不受限）；一次被策略拒绝的调用可经**用户批准的一次性行内提权**重试。
- **每平台后端**：Linux bwrap→Landlock（含原生 node addon）、macOS Seatbelt（sandbox-exec）、Windows 受限令牌 + ACL 写限制；共享策略解析器（`sandbox-policy`）按部署默认值 + 会话级覆盖解析出每次调用的策略。
- **同世界囚禁的边界**：沙箱只共享宿主内核与文件系统；容器/microVM/远程执行器是「整能力替换」，不走此缝。
- **fs / subprocess 缝的职责分离**：`ctx.fs`（后端可换：host / sandbox-enforcing）+ `ctx.subprocess`（一切子进程唯一出口：可执行文件查找、有界输出捕获、整树终止、净化启动环境）+ 模型侧工具（read/write/edit/glob/grep）——**后端更换不触碰工具与策略**。

## 3. 统一服务端：一份代码，三种部署

延续插件化计划的 profile 机制，新增第三个部署维度：

```text
                    ┌─ profiles/desktop ── Tauri sidecar 内嵌：server 插件 + 本地 Worker 插件
服务端（Fastify）────┼─ profiles/server ── Docker / 云端：server 插件（无 UI 依赖）
（同一棵插件树）     └─ profiles/worker ── 独立 Worker 容器（横向扩容时）
```

- **desktop profile** = server profile 的全部插件 + 本地存储驱动（见 §5）+ 本地能力节点（见 §6）+ loopback CORS（只允许 Tauri WebView 与本机浏览器来源）。
- **server profile**（Docker/云端）= 现有形态，Supabase 存储 + PGMQ 队列，多用户。
- 桌面端与自部署的差异**只体现在启用的插件与驱动**，不在代码分支。

## 4. 桌面端架构（Tauri 2）

```text
┌────────────────────── Tauri 2 应用（Rust core）──────────────────────┐
│  系统WebView窗口（WKWebView / WebView2 / WebKitGTK）                 │
│   └── Web UI（apps/web 静态产物，与 Web 端同码）                     │
│                                                                      │
│  Rust 层职责（薄）：窗口/托盘/自更新/深链/系统对话框/Keychain 凭证    │
│                                                                      │
│  Sidecar：服务端可执行文件（Fastify server + 内嵌 Worker）           │
│   ├── 127.0.0.1:<port> HTTP/WS（loopback，本机自签信任）             │
│   ├── 本地存储驱动（SQLite/PGlite + 内嵌迁移 + 本地队列）            │
│   └── 能力节点注册表 + 沙箱后端调用入口（经 Tauri IPC/Rust 桥）      │
└──────────────────────────────────────────────────────────────────────┘
```

**Sidecar 方案（决策点，推荐 A）**：
- **A. Node 独立可执行 sidecar**（推荐）：用 Node SEA 或 `bun build --compile` 把现有 Fastify 服务端打成单文件二进制，随 Tauri 资源分发。**零重写**——服务端插件树原样运行；代价是常驻内存约 80–150 MB（见 §8 预算）。
- B. Rust 重写服务端内核：内存最优，但等于大爆炸重写，违反本项目行为准则；仅作为远期选项（若未来仅移植 kernel 层）。
- C. Tauri Rust 层直接实现能力 + 无 sidecar：UI 与能力耦合，丢失「自部署同一套服务端」的统一性，否决。

**桌面端 Rust 层保持薄**：只做 Tauri 擅长的系统胶水（窗口、托盘、自更新、深链、Keychain、沙箱后端的 OS 调用），业务一律在 sidecar 服务端——保证桌面与自部署行为一致。

## 5. 存储缝升级（对插件化计划 v2 的修订）

v2 曾把「存储后端抽象」列为非目标。桌面本地优先形态出现了**真实第二消费者**，该缝升级为一等缝（仍然克制）：

```ts
// ctx.storage —— 三个窄接口，不做 ORM
StorageAdapter {
  auth:      RequestAuthenticator;        // supabase-jwt | local-trust（桌面本机免登录）
  db:        FeatureRepositories;         // 按 feature 定义 repository 接口，SQL 语义
  blob:      BlobStore;                   // 画布图/视频/上传文件
  queue:     JobQueue;                    // pgmq（自部署）| in-process（桌面）
}
```

| 驱动 | 部署 | db | queue | auth |
| --- | --- | --- | --- | --- |
| **supabase**（现有） | Docker / 云端 | Supabase Postgres（现有 `.from()` 逐步收拢到 repository 接口后） | PGMQ | Supabase JWT |
| **local**（新增，桌面） | Tauri sidecar | PGlite（WASM Postgres，SQL 语义最接近，复用迁移与 SQL 知识）或 SQLite（better-sqlite3） | 进程内队列（复用现有 executor 契约） | local-trust（本机回环免认证） |

- 迁移策略：Supabase 迁移 SQL 是唯一 Schema 来源；local 驱动消费**同一套迁移文件**（PGlite 直接执行；SQLite 需转译层——因此推荐 PGlite 起步）。
- 节奏：repository 接口的抽取跟随插件化计划 Phase 3 的 feature 迁移**同步进行**（迁移哪个 feature，就把它的数据访问收进对应 repository 接口），不另起大迁移。

## 6. 能力节点（Worker）体系

现有 `registerExecutor()` 注册表升级为**能力节点模型**，统一四种执行位置：

```text
Server（云端/自部署/桌面内嵌）
  ├── 内置 Worker（进程内或本机 sidecar，现有形态）
  ├── 独立 Worker 容器（Docker 横向扩容）
  ├── 桌面 Worker（本机：沙箱内 shell/文件/ computer-use，经 Rust 桥）
  └── 移动 Worker（受限：分享流入/相机/语音/通知）
```

- **节点注册**：Worker 启动后向服务端认证并声明 `capabilities: ["image_generation","video_generation","local.shell",...]`；服务端维护节点表（心跳、负载、能力清单）。
- **任务路由**：现有 PGMQ 任务类型 → 需要的能力 → 路由到具备该能力的节点；桌面本机任务优先本机节点（数据不出机），云端生成类任务可路由到任意节点（BYOK 凭证随任务加密下发或由节点自持）。
- **桌面特殊性**：本机 Worker 的 `local.*` 能力必须过 §7 沙箱与权限；云端/容器 Worker 默认全量能力（服务端即信任边界）。

## 7. 沙箱与权限体系（对标 dsh 三档模型）

- **三档模式**（沿用 dsh 词汇）：`read-only` / `workspace-write`（默认，画布工作区可写）/ `danger-full-access`（明示开启）；另有**一次性行内提权**：被拒调用弹窗说明原因，用户批准后单次放行。
- **平台后端**：macOS Seatbelt（`sandbox-exec`）、Linux bwrap→Landlock、Windows 受限令牌 + 工作区 ACL——Rust 层实现 OS 调用，sidecar 经 Tauri IPC/Rust 桥使用（dsh 的 landlock node addon 证明 Node 进程内同样可行，作为备选实现路径）。
- **能力授权矩阵（桌面设置页）**：每能力（本地文件读写范围 / shell / 浏览器控制 / 屏幕与输入 / 网络）独立授权；`danger-full-access` 需要二次确认。模型侧工具（read/write/edit/glob/grep/execute）从工具缝注册，**后端（host/sandbox）更换不触碰工具定义**（dsh fs 缝职责分离）。
- **computer-use**（远期）：对标 `nomi-computer`（screen/input/permissions），v1 先做屏幕截图 + 受控输入，画布场景优先级低于文件与 shell。

## 8. 内存与性能预算（拒绝 Electron 的具体含义）

| 项 | 预算 | 手段 |
| --- | --- | --- |
| 桌面空闲 RSS | **< 400 MB**（Electron 同类通常 600 MB+） | 系统 WebView（不捆绑 Chromium）；Rust core；sidecar 上限 150 MB |
| Sidecar 常驻 | 80–150 MB | Node SEA 单文件；懒加载插件（未启用 provider 不实例化）；Worker 复用同进程 |
| 渲染层 | 单 WebView 单窗口起步，画布虚拟化 | Excalidraw 按需挂载；大图走对象 URL + 缩略图；避免多窗口多 WebView |
| 安装包 | < 100 MB（不含 WebView 运行时） | 系统 WebView 复用；sidecar 压缩分发 |
| 移动端 | 薄客户端 < 150 MB | 无 sidecar；仅网络客户端 + 受限 Worker |

持续手段：启动后打印挂载树与各进程 RSS（开发模式）；内存回归纳入 workspace 测试门禁（超阈值告警）。

## 9. 开源策略（GPL-3.0）

- **许可证（决策点，推荐组合）**：客户端/桌面端 **GPL-3.0**；服务端 **AGPL-3.0**（网络服务条款防止他人拿服务端开 SaaS 却不回馈）。若偏好单一许可证，统一 AGPL-3.0。两者均为强 copyleft，符合「开源协作 + 防白嫖」的意图。
- **依赖兼容审计**：现有依赖（MIT/Apache-2.0/BSD）均与 GPL-3 兼容；`references/` 下项目仅作参考（deepseek-harness 为 MIT、nomifun 为 Apache-2.0），**引用其代码需保留版权声明并按各自许可处理，移植思路不复制代码**（沿用 AGENTS.md 参考项目规则）。
- **贡献基建**（随桌面端首发落地）：CONTRIBUTING.md + DCO（Signed-off-by，轻于 CLA）+ 行为准则；issue/PR 模板；`good first issue` 引流；插件生态：第三方插件独立仓库发布（对齐 dsh 的 `dsh-plugin` topic 模式），内核提供版本化插件契约。
- **治理与品牌**：商标与名称保护（注册 Loomic）；README 双语（中/英，现有 references 项目均有双语惯例）；赞助/资金通道（OpenCollective）后置。
- **仓库结构**：维持单 monorepo（apps/desktop、apps/server、apps/web、packages/*、crates/* 随桌面端加入），开源起步不分仓——降低贡献门槛。

## 10. 路线图（衔接插件化改造计划 Phase 0–7）

| 阶段 | 内容 | 前置 |
| --- | --- | --- |
| **P0–P7**（既有计划） | 内核、feature 插件化、供应商缝、BYOK 前端、profiles | — |
| **D1 存储缝** | `ctx.storage` 四接口 + repository 抽取（跟随 P3 feature 迁移同步做）；Supabase 驱动收拢 | P1 内核 |
| **D2 桌面壳** | Tauri 2 工程入库；Web UI 静态产物接入 WebView；sidecar（方案 A）跑通 loopback；local-trust 认证；系统托盘/自更新 | D1 + P5（BYOK） |
| **D3 本地存储驱动** | PGlite 驱动 + 同源迁移执行 + 进程内队列；桌面模式端到端离线可用 | D2 |
| **D4 能力节点** | 节点注册表 + 能力路由；桌面本地 Worker（进程内）；独立 Worker 容器镜像 | P6（executor 缝收编） |
| **D5 沙箱与权限** | 三档模式 + 三平台后端 + 授权矩阵 UI + 行内提权；fs/subprocess 缝落地（工具从缝注册） | D4 |
| **D6 自部署与 Web** | Docker Compose 文档化；Web 客户端服务端切换 + QR 配对（同 LAN） | P5 |
| **D7 移动端** | Tauri 2 Mobile 薄客户端 + QR 配对复用会话；受限移动 Worker（分享/相机/语音） | D6 |
| **OS-0 开源基建** | GPL-3.0/AGPL-3.0 许可证落位、DCO、CONTRIBUTING、双语 README、插件仓库规范 | D2 前完成 |

顺序铁律：**先服务端内核与 BYOK（P0–P7），后桌面（D1–D3），再本机能力（D4–D5），客户端形态最后（D6–D7）**——桌面与移动的每一层能力都依赖服务端缝先就位，避免为壳先写业务。

## 11. 待决策清单（开工前拍板）

## 12. 风险与非目标

| 风险 | 对策 |
| --- | --- |
| Linux WebKitGTK 行为碎片化（渲染差异/版本） | CI 矩阵覆盖三平台；Linux 上考虑 WebKitGTK 4.1 固定 + 已知问题清单 |
| Node sidecar 内存与冷启动 | 预算门禁（§8）；懒加载插件；超标则评估 bun compile 或内核 Rust 化（仅 kernel 层） |
| Tauri Mobile 成熟度（iOS 审核/插件生态） | 移动端排最后（D7）；薄客户端不依赖冷门插件；不可行时退化为 PWA 连接服务端 |
| 沙箱逃逸 / 本机能力滥用 | 默认 `workspace-write`；能力默认关闭、明示授权；提权审计日志；danger-full-access 二次确认 |
| PGlite 与 Supabase 行为差异（RLS/扩展） | repository 接口层隔离差异；RLS 逻辑属服务端层不在 local 驱动复现；差异清单随 D3 维护 |
| GPL 审计疏漏引入不兼容依赖 | 依赖变更走 license 检查（纳入 knip/hygiene 门禁） |
| 范围失控（形态多、能力多） | 铁律「服务端缝先就位」；每阶段独立可交付；非目标明确拒绝 |

**非目标（明确不做）**：不做 Electron；不做 Rust 全栈重写；不做 P2P 多机数据同步（多端连同一服务端，v1 无 CRDT）；不做 iOS/Android 原生独立 App（Tauri Mobile 或 PWA 二选一）；云端托管 SaaS 的多租户计费体系不在本计划（沿用现有 credits，仅云端形态启用）。
