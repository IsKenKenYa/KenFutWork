# 桌面端与多端架构计划（Tauri · 三形态）

> 状态：**计划稿 v0（概念阶段，未实施）**
> 定位：本计划是《插件化改造计划》的**姊妹计划**。该计划 §8 将「桌面/local-first 形态」与「脱离 Supabase 的存储后端」列为非目标并注明「届时另立计划」——**本计划即那个另立计划**，同时修订其 §1.3「保持 web 平台形态」的产品决策。
> 决策记录：2026-09-02 产品拍板，转向**桌面为主、三形态并存**（桌面全本地 / 自托管 / 云托管），继续 GPLv3 开源。

## 1. 产品形态

| | 桌面全本地（主形态） | 自托管 | 云托管（现状演进） |
| --- | --- | --- | --- |
| 服务端 | Tauri 内嵌 sidecar（本机进程） | Docker Compose（用户机器/NAS/VPS） | 平台托管 |
| 数据存储 | 本机（PGlite/SQLite，Spike S2 定） | 自托管 Postgres + 对象存储 | Supabase |
| BYOK Key | OS 钥匙串 | 服务端加密落库 | 服务端加密落库 |
| Worker 能力 | 完整（本机操控） | 部署机上的受限子集 | 不开放 |
| 适用 | 个人创作者（默认形态） | 团队 / homelab / 多端同步 | 不想自管的基础用户 |

设计原则（继承仓库准则）：

1. **单一 UI 产物、单一服务端代码库**：形态差异只表达为 profile 装配差异，不为桌面写第二套后端，不为桌面 fork 前端。
2. **能力即缝**：每个形态差异（存储 / 认证 / 队列 / 本机工具）都是缝三元组，禁止 `if (isDesktop)` 散弹式分支。
3. **BYOK 与隐私优先**：数据与 Key 的默认存放位置随形态下沉到用户侧。
4. **内存是硬指标**：不用 Electron 是起点不是终点，预算见 §4。

## 2. 总体架构

```
                    ┌────────────────────────────────────────┐
                    │            单一 UI 静态产物              │
                    │   apps/web（Next.js output:"export"）    │
                    └──────┬───────────┬───────────┬─────────┘
                           │           │           │
        ┌──────────────────▼───┐  ┌────▼───────┐  ┌▼────────────────┐
        │ 桌面：Tauri 2 壳      │  │ 浏览器      │  │ 移动：Tauri 2    │
        │ · WebView 加载同一份  │  │（自托管/云）│  │ iOS/Android     │
        │ · Rust 能力网关（§5） │  └────┬───────┘  │ 瘦客户端 + 受限  │
        │ · sidecar 进程管理    │       │          │ Worker          │
        │   └─ loomic-server    │       │          └───────┬─────────┘
        │      desktop profile  │       │                  │
        │      （一进程）        │       │                  │
        └──────────┬───────────┘       │                  │
                   ▲ 127.0.0.1 + pairing token            │
                   └───────────┼──────────────────────────┘
                               ▼
        ┌─────────────────────────────────────────┐
        │ 自托管：Docker Compose                   │
        │ server（托管静态 UI）+ worker + PG/pgmq  │
        │ + 对象存储 +（可选 auth 组件）            │
        └─────────────────────────────────────────┘
```

核心决策：

- **D1 桌面 = 壳 + 内嵌服务端，不是纯客户端。** 本机文件、沙箱、操控类 Worker 能力必须有本地运行时；顺带获得离线可用与 Key 本地化。纯客户端 + 云无法承载「操控本机」。
- **D2 服务端零分叉。** 复用 `apps/server` 全部代码；桌面 = 新增 `profiles/desktop.ts`（server profile + worker profile 合并为**单进程**，队列换实现），由插件化蓝图 §4.5 的 profile 机制原生承载。
- **D3 UI 单产物。** `apps/web` 已是 `output: "export"` 静态导出：桌面 WebView 与自托管 server 托管**同一份静态文件**。前置改造：`NEXT_PUBLIC_SERVER_BASE_URL` 等是构建期烘焙的，必须改为运行时注入（Tauri 启动参数 / `window.__LOOMIC_RUNTIME__` / 相对路径），否则桌面无法在「内嵌服务端 / 远程服务端」间切换。
- **D4 sidecar 打包**：目标 = 单文件 Node 服务端可执行。候选 Bun `--compile`（首选，体积与启动占优）与 Node SEA（兜底，Stability 1.1 实验性、原生模块须按资产打包）→ **Spike S1 先行**（§10）。
- **D5 移动端 = 瘦客户端 + 受限 Worker 子集。** iOS 无 JIT、无后台常驻、文件系统沙盒化，sidecar/Node 方案在 iOS 不可行——这是平台硬约束，不是产品选择。
- **D6 网络自带（BYON）。** 产品不做内网穿透/中继服务：手机连桌面走 LAN（mDNS 发现 + 二维码配对），跨网走用户自有通道（Tailscale / 自有 VPS 反代）。多端同步能力绑定用户选定的服务端。

## 3. 服务端：新增能力缝

前置：插件化蓝图 Phase 0–7 完成后开工。以下全部按三元组（Definition + Provider + Consumer）设计，新增 ctx key 须同步蓝图 §4.2。

| 缝 | Definition | Provider（按形态） | Consumer |
| --- | --- | --- | --- |
| `persistence`（新增 key） | 各聚合 repository 接口（projects / canvas / threads / …） | cloud / selfhost = Supabase 实现；local = 嵌入式 PG 实现 | 各 feature 插件 |
| `auth`（既有 key，加实现） | `RequestAuthenticator` | cloud / selfhost = Supabase JWT；local 与 selfhost 单用户档 = 本地 token | HTTP 中间件、ws |
| 队列（`jobs` 下可替换） | JobService 队列接口 | server / selfhost = PGMQ；local = 同进程 SQLite 队列（Node ≥22 内置 `node:sqlite` 或 Bun `bun:sqlite`，避免原生模块进 sidecar） | worker profile |
| 凭证（收拢在 `modelProviders` 内的 SecretStore） | `SecretStore` 接口 | cloud / selfhost = 服务端加密表；local = OS 钥匙串（经 Tauri IPC） | 模型实例化 |
| `toolsGateway`（新增 key） | 本机工具调用统一闸门（scopes 校验 / 确认策略 / 审计） | desktop = Tauri IPC → Rust 执行器；selfhost = HTTP 到部署机 agent 执行器 | `agent/tools` 本机类工具 |

**存储缝是本计划最大的单项工程**（蓝图曾明言关系数据不做抽象，本计划正式重启它）。两条候选路线，Spike S2 定夺：

- **路线 A（推荐）：嵌入式 Postgres（PGlite，WASM）**。直接重放 `supabase/migrations/` SQL（方言一致，无第二套 schema 漂移）；RLS 在单用户 local 模式下用固定本地角色或裁剪。代价：需要 local 兼容迁移层（auth/storage schema 在裸 PG 中物化为本地表、剔除 Supabase 专有对象）。最大优点是迁移账本与生产同源。
- **路线 B：SQLite + 平行 schema**。实现轻，但「`supabase/migrations` 唯一迁移源」红线被打破（PG 方言不可重放），schema 双维护漂移风险长期存在。

关于 PGMQ：local 队列不追求 PGMQ 语义对齐，实现同一 JobService 接口即可（executor 契约不变）；PGlite 能否加载 pgmq 列入 S2 顺带验证。

## 4. 桌面端（Tauri 2）

**为什么不是 Electron**：Tauri 用系统 WebView（macOS WKWebView / Windows WebView2 / Linux WebKitGTK），不打包 Chromium，最小应用在 KB 量级，内存与体积是数量级差距。代价：三端 WebView 行为差异要当一等公民测（尤其 Linux WebKitGTK 跑 Excalidraw 画布，Spike S3）。

**进程模型**：

```
loomic.app
 ├─ Rust 主进程（TAO 窗口 + WRY WebView）
 │   · 加载 http://127.0.0.1:<随机端口>（sidecar 托管的静态 UI）
 │   · 能力网关（§5）：fs / shell / 截图 / 剪贴板 / 通知 → 权限闸门 → 执行
 │   · 生命周期：拉起 / 看守 / 终止 sidecar；开机自启；深链；文件关联
 └─ loomic-server sidecar（单文件可执行）
     · desktop profile：Fastify（HTTP+WS）+ worker 合一进程
     · 托管静态 UI（与 web 同一份产物）
     · 仅绑定 127.0.0.1 + 随机端口 + pairing token
```

Tauri 侧插件清单：`shell`（sidecar 管理）、`fs`（scope 受限）、`dialog`、`notification`、`clipboard-manager`、`global-shortcut`、`deep-link`、`autostart`、`single-instance`、`updater`、`stronghold`/`keyring`（钥匙串）。

**内存预算（目标值，Phase B 实测后转为验收线）**：

| 组成 | idle 目标 | 工作态目标 |
| --- | --- | --- |
| WebView（画布页） | 120–180 MB | 300 MB |
| loomic-server sidecar | < 150 MB | 400 MB（含 agent 运行） |
| Tauri Rust 主进程 | < 60 MB | 80 MB |
| **合计** | **≤ 350 MB** | **≤ 800 MB** |

优化手段：server + worker 单进程合并（D2）；LangChain/deepagents 等重依赖懒加载（首次对话才 import）；local 模式不加载 Supabase SDK；单 WS 连接复用全部事件流；画布大对象虚拟化、按需加载。

**打包与更新**：Tauri `externalBin` 声明 sidecar（按 target triple 后缀分发三平台二进制）；更新走 `tauri-plugin-updater` + 自托管更新清单。签名成本列入：macOS 公证（Apple Developer 年费）、Windows 代码签名证书、Linux 无强制。

## 5. 本机 Worker：能力、权限、沙箱

**能力清单（对标 nomifun 及同类桌面 agent 产品的通用 Worker 面）**：

| 能力 | 载体 | 落地阶段 |
| --- | --- | --- |
| 文件读写 / 搜索 / 移动（scope 到授权目录） | Rust fs + 权限闸门 | C |
| Shell 执行（白名单 + 确认） | Rust 沙箱包装进程 | C |
| 剪贴板 / 通知 / 打开 URL 与应用 | Tauri 插件 | C |
| 目录监听、文件索引 | notify / walkdir + ignore | C |
| 截图 | xcap | C |
| 浏览器自动化 | CDP 控制用户自有浏览器（不内嵌） | D |
| 输入操控（computer-use 级） | enigo | E（默认关闭，显式开启） |

**权限模型（toolsGateway 缝的语义）**：

- 每个工具声明 scopes：路径范围、命令模式、网络 egress 域。
- 三态策略 allow / ask / deny，**默认 deny**；ask 弹 Tauri 原生确认框（记忆粒度：本次 / 本会话 / 永久）。
- 全量审计日志（本地库：谁、何时、动作、参数摘要、结果摘要；含敏感内容时脱敏）。

**沙箱分层（务实渐进）**：

- L0（阶段 C 必须）：闸门 + 路径 allowlist + 路径穿越防护 + egress 默认拒绝。
- L1（阶段 C–D 分平台）：macOS 用 Seatbelt profile 包裹 shell 子进程；Linux 用 Landlock（Rust 原生）+ 可选 bubblewrap；Windows 用受限令牌 + Job Object。
- L2（阶段 E）：网络 egress 强制过代理点，agent 发起的网络请求全部可审计。

**威胁模型要点（「能操控本机」的产品，一号风险是 prompt injection）**：

- 任何不可逆 / 越权动作必须过人审闸门，agent 没有「自我授权为永久允许」的路径；
- 网页、文档、工具结果进上下文前清洗注入模式；
- 恶意工作区内容不得扩大 scopes；
- loopback 上的其他本机进程：所有 HTTP/WS 校验 pairing token + Origin，防本地 CSRF 式劫持。

## 6. 移动端

Tauri 2 同库出 iOS / Android，UI 复用静态产物（移动端另做响应式适配层）。能力矩阵：

| | iOS | Android |
| --- | --- | --- |
| 瘦客户端（画布 / 对话 / 审批 / 通知） | ✅ | ✅ |
| 媒体采集（相机 / 相册 / 语音） | ✅（picker 沙盒内） | ✅ |
| 分享入（系统分享到 Loomic） | ✅ | ✅ |
| 后台任务 | 仅 BGTask 窗口内短任务 | 前台服务（带常驻通知） |
| Shell / 文件系统 | ❌ 平台禁止 | 受限提供（默认关闭） |
| 承载服务端 | ❌ 不可行 | ❌ 不做（非产品方向） |

「手机 Worker」定位为 **capability 子集**：手机作为受限执行端挂到用户选定的服务端（桌面或自托管），不承载服务端本体。连接方式：mDNS 发现 + 二维码配对（pairing token 交换并存钥匙串）；跨网连接 = 用户自有通道（D6）。

## 7. 自托管（Docker）

- 基线已有（server 已有 Dockerfile），扩展为官方 Compose：`server`（托管静态 UI）+ `worker` + `postgres`（pgmq）+ `minio`（对象存储）+ 可选 auth 组件。server 与 worker 可合并为单镜像双 profile 启动（蓝图 profile 机制的自然产物），降低 compose 复杂度。
- 认证两档（产品决策见 §12）：单用户 token（家庭 / 单人，零外部依赖）与多用户（Supabase self-host 或等价 auth）。
- 升级纪律完全沿用仓库「数据库迁移」章节：镜像版本与迁移账本绑定、先备份、只前向修复、禁止覆盖校验和。

## 8. 安全与隐私

- 本地服务面：仅绑 127.0.0.1、随机端口、pairing token 全量校验；HTTP/WS 复用现有鉴权缝。
- Key 红线不变（只写不读、日志脱敏、前端永不回显）；local 模式下 Key 落 OS 钥匙串，经凭证缝读取，明文只在服务端内存短暂持有。
- 遥测默认关；审计数据本地存。
- 供应链：GPL 仓库引入新依赖需过许可兼容检查（§9）。

## 9. 开源与 GPL v3

- **主仓库 GPLv3**：全部原创代码 GPL 化。现有依赖链（Tauri MIT/Apache-2.0、LangChain MIT、deepagents MIT、Excalidraw MIT、Next/Fastify 等主流宽松许可）均与 GPLv3 兼容，可合入。
- **插件生态边界（写进 README / CONTRIBUTING）**：经公开扩展点 API（ctx key / 缝接口）、独立仓库独立分发的插件视为独立作品，作者自选许可；仓库内插件目录并入 GPL。这是 GCC 插件同款立场，是社区活力的前提。
- **贡献协议**：DCO（`Signed-off-by`），不强制 CLA——保住「全世界开发者无门槛共建」的初衷；未来确有需要再议。
- **商标与代码分离**：项目名注册商标。GPL 授予的是代码权，不授予商标权——fork 可用代码，不可冒用名字。
- **已知取舍（AGPL 问题）**：GPLv3 无网络条款，他人把改版当 SaaS 托管不触发开源义务。若在意「云厂商白嫖」，可对 `apps/server` 单独用 AGPL-3.0，但双许可复杂度高、部分贡献者会被吓退——初期不建议，记录为已知取舍，商业化前重新评估（§12）。

## 10. 路线图

**前置铁律：插件化蓝图 Phase 0–7 必须先完成。** profile 机制、feature 插件形状是本计划的地基；存储缝重启也依赖 feature 先收拢成插件，否则 repository 化没有干净的挂载点。

| 阶段 | 内容 | 验证门 |
| --- | --- | --- |
| **A. 缝定稿 + Spike** | §3 缝接口契约定稿（packages/shared 先行）；Spike S1–S4 | Spike 结论文档 + 契约评审 |
| **B. 桌面 POC** | Tauri 壳 + sidecar + `NEXT_PUBLIC_*` 运行时注入改造 + desktop profile 单进程 + persistence/auth/queue 的 local 实现 | 三平台出包；画布可用；离线可用；内存达预算线 |
| **C. 本机 Worker** | toolsGateway + 权限闸门 + 确认 UI + 审计 + 文件 / shell / 截图等工具 | 越权用例全拒；prompt injection 用例不逃逸；审计可回放 |
| **D. 自托管 + 远程连接** | Compose 全家桶 + 桌面 remote 模式（URL / 配对切换）+ 手机连接 | compose up 全链路冒烟；桌面双形态切换；QR 配对成功 |
| **E. 移动端** | iOS / Android 壳 + 受限 Worker 子集 + 后台策略 | 双平台真机过 §6 能力矩阵 |
| **F. 发布工程** | 三平台签名 / 自动更新 / 插件目录 / 文档站 | 全自动发布流水线 |

Spike 清单（阶段 A 内完成，每项出结论文档）：

- **S1 sidecar 打包**：Bun `--compile` 打包 `apps/server`（LangChain / deepagents / pg 驱动兼容性）vs Node SEA（原生模块资产化、跨平台 CI 矩阵：SEA 官方 CI 仅测 mac arm64 等）。兜底：内嵌 Node runtime 目录随包分发。
- **S2 存储缝**：PGlite 重放迁移（auth / storage 兼容 shim 工作量评估）vs SQLite 平行 schema。据此定路线 A/B。
- **S3 WebKitGTK 渲染**：Excalidraw 画布在 Linux WebView 下的性能与兼容性。
- **S4 内存基线**：现有 server 在本地最小配置下的 idle RSS，校准 §4 预算线是否现实。

## 11. 风险登记

| 风险 | 等级 | 对策 |
| --- | --- | --- |
| 存储缝工作量失控（本计划最大单项） | 高 | 路线 A/B 由 Spike 早定；repository 逐聚合迁移；local 首版允许只覆盖核心聚合（画布 / 对话 / 设置） |
| Bun / SEA 兼容性 | 高 | S1 先行；兜底内嵌 Node runtime |
| WebKitGTK 画布性能 | 中 | S3；不可接受则 Linux 降级为「自托管 + 浏览器使用」 |
| iOS 平台限制致体验落差 | 中 | 定位即瘦客户端，预期管理写进产品文案 |
| 内存超标 | 中 | 预算线进 Phase B 验收门；超标先砍常驻依赖（懒加载已列） |
| `NEXT_PUBLIC_*` 动态化改动面 | 中 | 阶段 B 首个 PR，靠编译器牵引 |
| 双形态 schema 漂移（仅路线 B 存在） | 中 | 优先路线 A 规避 |
| 多线并行带宽不足 | 高 | 严格按拓扑序；桌面 POC（B）完成前不启动移动端（E） |

## 12. 待产品决策（实现前必须定）

1. **自托管认证档位**：单用户 token 是否为首发档；多用户档何时做。
2. **server 是否单独 AGPL**：§9 初期建议纯 GPLv3；商业化前重评。
3. **local 模式计费件**：`credits/tierGuard/payments` 在 desktop profile 建议 `enabled=false`；平台托管模型池（平台 Key 池）在 local 模式是否提供。
4. **商业化形态**：GPL 下卖什么——托管服务、官方增值模型池、企业支持。影响 §9 许可细节。
5. **产品名与商标**：GPL 项目名必须独立于代码注册。
