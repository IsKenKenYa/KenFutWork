# 进程沙箱 module

`types.ts` 是公开 Definition；`service.ts` 是 Provider；`consumer.ts` 将执行作用域接到 Provider。内核插件与 profile 由宿主装配。这里不持久化第二份 Task/后台工作状态，只有 Task 的原始进程句柄、授权版本屏障和输出引用。

开发态每 Task fork `task-helper.ts`，只载入绝对 tsx loader，不继承 API 的 `--env-file`、watch 或 provider/database 环境。发布态通过 `helperPath`/`nodePath` 注入独立 Node helper。生产构建：

```sh
node apps/server/src/features/process-sandbox/build-helper.mjs release/process-helper
cargo build --manifest-path apps/server/src/features/process-sandbox/native/Cargo.toml --target x86_64-pc-windows-gnu --release --locked
node apps/server/src/features/process-sandbox/build-helper.mjs release/process-helper apps/server/src/features/process-sandbox/native/target/x86_64-pc-windows-gnu/release/kenfutwork-process-broker.exe
```

发布资源中 `process-helper/` 保留 helper、固定 SRT 0.0.78 的完整 npm runtime 依赖、vendor 资产及来源/许可证；独立 Node 沿用宿主 `runtime/node/` 布局。Linux 还需要 bwrap、socat、rg；缺少能力不裸跑。Node SEA 本体不能拿来当 `nodePath`，应传随包的真正 Node binary。

Unix 使用 SRT 的 OS profile，每 Task 隔离单例/proxy。任务目录权限逐调用传完整 policy；模型的 command/env/shell 不进入未约束的宿主 launcher。SDK 输出的 argv 以 `shell:false` spawn。输出为到达顺序的有界原始 byte capture；`discardedBytes` 明示超过上限的数据量。`readOutput` 默认读取合并流，可显式传 `stream: "stdout" | "stderr"`；Git 解析成功结果必须只读 stdout。stdout/stderr 的保留字节合计等于 merged 的保留量，共用一条采集 cap，不另给每流 cap；分流日志是 merged 的磁盘副本，三文件合计空间最多为保留数据量的两倍。未完成 UTF-8 尾部保留游标，下一次读取在字节到齐后返回完整字符。每个 wrapper 恰好一次 cleanup，所有目标范围退出以后 reset。

原生 Windows 由独立 Rust broker 改编 Codex MXC/PSEC 路径；每个命令有独立内核读取域与 Job，不改全局 sandbox-users ACL。固定 Microsoft MXC `6cd3d58f05d3447e67109cfb75e042803b843ca4`，禁 DACL mutation/学习模式降级。SDK suspended→assign Job→resume，kill/wait 在清空 Job 以后才释放读域。当前 SDK 不具备 client-only 的受限 host-loopback posture；非空网络域列表直接返回 `enforcement_unavailable`，而非扩大网络权限。Windows build 不支持 PSEC/deny path 时同样拒绝执行。

macOS 普通 pipes 的托管范围是 POSIX process group，PTY 是原生 SID/birth 签发的 session；Linux 是 bwrap PID namespace及其嵌套 namespace；Windows 是 Job。`ProcessEnforcement.processRange` 报告真实范围，不能把进程组描述成不可逃逸的任意后代容器。权限收紧先拒新 spawn/stdin，再停被收紧影响的旧进程，等待实际范围退出。扩权保留原进程 policy；不会把放宽后的范围施加到它。停止失败不提供 `rangeEmpty:true`。每 Task 的 scope change/revoke/close 串行排队，旧回调不能解除新屏障；旧代际 close/revoke 被拒绝。macOS 若 signal-0 在本 helper 的未 reap zombie 窗口返回 EPERM，只继续等待；仅 ESRCH 能确认进程组为空，宽限期超时仍报告未确认。关闭后句柄可复用已收到的退出事实，可信新代际只有在旧 helper 确认关闭后才能重开。

`spawnCheckpoint` 是固定的系统 consumer authority；Profile 的 `resolveInternalWriteRoots(scope, "checkpoint")` 返回精确 Task 影子仓库路径。普通 spawn 不接受额外内部根。CodeExecutionScope 和模型 argv/env 不签发该 authority，用户工作目录权限不因此扩大。

`readonlyExecution` 由 provider 的固定网络deny profile推导（支持平台、没有不透明的 per-Task network resolver、allowedDomains为空）；它表示requestedScope只读时用户目录只读且无网，并非宣称运行依赖已probe就绪。实测同一Task先RW helper后RO请求：文件改写与本机HTTP连接都被阻止。临时目录先realpath，HOME放在Task私有temp/home以支持CLI缓存；capture/probe目录仍单独禁止命令读写。

`acquireRestoreBarrier(scope, roots)` 协调本provider进程的用户目录写域。第一次await前预留requestedScope，覆盖冷helper/policy准备；跨Task相交的pending/活RW进程返回409且不自动杀。持有期间新相交RW请求拒绝，RO请求及只写private metadata的RO checkpoint仍可执行。只有可信rangeEmpty退出事实释放writer；失联/stop未确认不能当gone。release幂等。实测readonly checkpoint先初始化不会限制合法main RW，parent先RW也不会放大readonly子请求。外部shell/editor仍由版本观察防冲突，不宣称受此应用内barrier管理。


## 完整 stdio 协议 consumer seam

`spawnStdio(ProcessStdioSpawnRequest)` 接受精确 argv、Task scope、agent/invocation 与显式 env；返回 ManagedStdioProcess（onStdout/onStderr、writeStdin、真实 endStdin EOF、stop/wait/snapshot）。stdio 使用真实 pipes，绝不拿 PTY 替代。两条 stream 的 UTF8 StringDecoder、sequence 与 full byte cursor 独立，listener Promise 完成后每流 ACK；启动到挂载前保留 pending 并暂停对应pipe，历史 capture cap 不截断协议。

Unix source helper首 public tracer actual RED spawnStdio missing → GREEN1/1，日志 `/private/tmp/kfw-code-harness-stdio-green.log`（420ms）：isTTY=false、完整独立startup stdout/stderr、跨chunk UTF8中、显式literal env、stdin EOF与exit0/rangeEmpty、超过128bytes历史cap仍送EOF_DONE，capture实际truncated。

MCP consumer须同时挂 stdout/stderr reader 再等待退出；waitForExit join两个活跃reader的delivery/ACK。权限撤销/关闭继续同Task helper真实进程范围。Windows完整逐流ACK需要native broker线程适配，尚未完成时显式fail closed，不能用capture轮询冒充完整协议流。

PTY发布artifact曾由父代理真实consumer验收2/2 GREEN；新增stdio/RPC后请使用最新重build artifact。Linux 真沙箱 PTY 已完成下节实测；Windows ConPTY 与完整 stdio ACK 仍是整体 Goal 未完项，stdio 不替代 PTY。


## Linux 实机完成回执（2026-10-03）

固定 SRT 0.0.78 的 `--new-session` 只在 PTY invocation 中移除，由 node-pty 自己签发独立 session/TTY。`linux-launch.ts` 解析且验证 inline 与 args-file 的精确 wrapper；保留 fs/network/seccomp、`--die-with-parent`、PID/user namespace与fresh `/proc`，未知形状 fail closed。强 denyRead('/') 下发现两个 pinned SRT mount 顺序问题：前置内部 observer/proxy socket bind 被后续 `/tmp` tmpfs 遮蔽；private metadata 的 denyRead tmpfs 为可写占位层。适配仅重放相同精确 socket bind，并在所有 mount 后将 private tmpfs remount read-only，绝不放开 `/tmp` 父树或弱 nested sandbox。隔离探针按 Linux tmpfs 的 ENOENT 与真实只读错误码判定，并在失败时仅报告 read/write 错误码。

## Windows 源码与可做验证回执（2026-10-03）

固定 MXC 的 ordinary `kill/wait` 一手源码使用 `terminate_best_effort`，Job drain timeout只是warning后继续teardown，故不能将其单独当strict rangeEmpty证明。当前实现保留原固定依赖与许可，没有vendor/patch共享SDK。每个Windows command使用同nativebinary的可信controller；broker将controller以CREATE_SUSPENDED创建、赋外层Job后才resume，再经private anonymous handles发送launch DTO。用户argv/env只由原MXC/PSEC消费，不在controller/broker之外裸跑。controller在SDK wait/teardown前确认外层Job只剩自己，broker最后确认Job为0。query handle只有JOB_OBJECT_QUERY，control/query继承位在user spawn前清除；SDK仍走原suspended→Job assign→resume与独立PSEC读取域。

PTY使用真实CreatePseudoConsole与ResizePseudoConsole，broker读写原始ConPTY流，controller在其console中用MXC Inherit；双流stdio使用MXC Pipes。private control IPC与raw tty分离；Root stdin写不会占住stop/ACK循环。raw base64 native frame每stream单帧ACK，helper StringDecoder将native raw序号映射到独立UTF8交付序号，空分片先ACK、EOF刷新尾部、active reader原生exit时保留回压与最后ANSI。capture上限不截协议。自然退出等待user range、输出reader与ACK；早停不等待spawn ready。输出交付失败与物理退出Promise分开，未知Job/IPC失联不能借输出结束解锁。Windows默认HOME/USERPROFILE/APPDATA/LOCALAPPDATA落Task private temp/home，显式env只应用到PSEC用户命令。

native v2 probe真实检查PSEC/deny path、Job与ConPTY，公开spawnPty/spawnStdio按实际capability握手接线；旧binary/能力缺失fail closed，不以pipes伪装TTY。非空network域列表仍因固定SDK不支持client-only受限代理而拒绝，不扩大权限。
