- code-ui插件动态注册严格 `{plan:完整Markdown}` 的主Code ExitPlanMode，可信planControl=exit不声明资源access。原permission policy即使yolo也返回ask；原admit/peek/最终claim与取消信号继续持有一次授权，不造broker、Run或resume loop。Enter/Exit复用同一真实主Task/Run绑定校验，worker/explore/review/shared不能拿控制标记扩权。
- 原PendingInteraction为userInput，schema.interaction=plan_approval/toolName=ExitPlanMode；实际题文与approve/reject选项沿原Elicitation。只有实际题文的明确approve可签发；空accept、自由文本、普通权限记忆、不足或矛盾answers都拒绝并保留等待。拒绝/cancel不关闭规划。普通Ask/permission解码保持原行为。
- 新Task私有planningEpoch只在同一根锁内比较前后持久planEnabled推进；token、usage与工具流事件不推进。Conversation恢复与export持有epoch/approvedPlan；原V4 schema和Todo的snapshot.plan不变。真实request身份/签名、live回答、最终claim及文件后的Task提交均核规划epoch，不能将旧批准用于新episode。
- CodeApprovedPlanStore接口、管理FS Provider和规划Consumer完整接线。唯一根为LocalInstance.resolve(actor).dataDir，沿resolveDesktopPaths的sandbox/agent-files保存；不能用测试env.agentFilesRoot替代、不能加入Task附加目录或把管理ref作为普通文件路径。逐级realpath核管理目录，UTF-8原字节flush、不可覆盖发布并逐字读回成功后，才在根锁发布approvedPlan及flag=false；发布前后继续核真实Task/Run/两代际与取消。数据目录迁移准入沿原beginAdmission/assertReady。
- 原工具observer持有canonical/native/V4成功或失败；文件失败不写批准事实、不关闭flag，返回原Harness工具错误，后续Write仍正式拒绝。完整Markdown留原toolCall.input.plan及批准结果，原卡片/查看全文源链可消费；未修改原ZCode UI字节，也未进行该入口DOM点击验收。

## 持久副作用合同

稳定键由宿主生成：Task事件 `plan-exit:${runId}/${toolCallId}`（在实例/Task内），管理文件planId为原ApprovalIdentity（含Task/Run/call/两代际/规划epoch）的规范SHA-256，正文不进入幂等键。审批签名绑定身份、规范参数和控制效果；Task事件指纹额外绑定原始Markdown、实际文件ref/hash，同键异参拒绝。管理目标为同Task专属不可覆盖 `.md`，顺序/并发相同调用读回同ref，不同正文不能覆盖。

FS与PG不做虚假的跨介质事务：先生成并flush管理文件，再在Task根锁内CAS批准事实/flag；失败可能留下无批准引用的管理文件，但不放权、不复活已删除Task、不自动重放原工具。原claim每调用只消费一次。响应丢失仍从Task持久批准事实/工具事件读回，不借重复claim执行；数据根搬迁保留相对ref。Task删除/撤权/Run停止在发布前重验，最终实例物理删除随数据目录清除；冷恢复与删除后的迟到RPC专属验收仍未完成。
